# IntellectFS (IFS) v1.0 — полная проектная спецификация файловой системы IntellectOS

**Статус:** `DESIGN DRAFT / NORMATIVE TARGET / НЕ РЕАЛИЗОВАНО`  
**Дата проектирования:** 20 ноября 2026 года  
**Назначение:** собственная высокопроизводительная локальная ФС для IntellectOS Server и Desktop, с единым нативным контрактом транзакций, целостности и восстановления.  
**Наименование:** **IntellectFS**; сокращение **IFS**; тип тома `intellectfs`; рекомендованная метка раздела `IFS_ROOT`; UUID тома — 128 бит.  
**Версия дискового формата:** `1.0` (проектируемая первая версия, а не переход с другой).  
**Язык описания:** русский; имена API и wire-полей — английские.  
**Лицензия:** этим документом не назначается.  
**Главное ограничение:** документ не подтверждает эксплуатационную готовность, испытания на реальном SSD, формальную верификацию либо превосходство над существующими ФС.

> В данной спецификации **MUST / ОБЯЗАН** обозначает обязательный инвариант; **SHOULD / СЛЕДУЕТ** — предпочтительное решение, допускающее документированное исключение; **MAY / МОЖЕТ** — опциональную реализацию. «Сохранён после отказа питания» всегда означает отказ при **соответствующем спецификации** блочном устройстве, контроллере, драйвере и корректно реализованной семантике Flush/FUA. Никакой программный формат не гарантирует сохранность при контроллере, который отвечает об успешном Flush, но не делает данные энергонезависимыми.

## 0. Решение об архитектуре

### 0.1. Что мы строим

IntellectFS — **нативная объектно-экстентная CoW-файловая система** с проверяемыми корневыми указателями, теневыми обновлениями, независимыми группами размещения, журналами публикации *seal*, сквозными контрольными хешами, явными транзакциями и возможностью адресовать данные по стабильному OID. Она является **собственной ФС IntellectOS**; НЕ является форком AetherFS, ext4, XFS, ZFS или Linux VFS.

Основной путь:

```text
Vibelang / IVX application / system service
                  │
        Native IntellectOS FS API
                  │
          Handles / capability
                  │
     VFS namespace + object cache
                  │
    IntellectFS trusted state engine
       ├─ directory and OID indices
       ├─ extent / snapshot indices
       ├─ transactional seal writer
       ├─ allocation / GC / scrub
       └─ page cache and async I/O
                  │
     IntellectOS BlockDevice API
                  │
    AHCI / NVMe / virtio-blk drivers
                  │
       regular SSD / virtual disk
```

Базовые цели: **целостность сначала, минимизация лишних записей затем, параллельность без глобального пути блокировок, предсказуемые p99/p99.9, загрузка серверной ОС без GUI**. ФС не использует ИИ для принятия решений, влияющих на корректность данных. ИИ может рекомендовать политику кэширования, но его результаты проходят ограничения доверенного движка.

### 0.2. Почему не переносим AetherFS дословно

Приложенное исследование «Современные и экспериментальные файловые системы» описывает AetherFS, которую предполагается строить над Linux, io_uring, FUSE, sched_ext, eBPF, MPK/UINTR, CXL и FoundationDB. Эти компоненты **не существуют** в нашем текущем ядре. Используем идеи — не зависимости и не обещания результатов. Особенно неприемлемо кодировать в постоянный формат предположение о конкретном процессоре Intel, честной 4-КиБ атомарной записи, NVMe FDP, кластерной когерентности CXL или глобальной согласованности FoundationDB.

В предоставленных пользователем замечаниях второго ИИ особенно ценны: единый `begin → mutate → seal`, устойчивая идентичность объекта, 4-КиБ проверяемые публикации без предположения атомарности, сохранение предыдущего корня, CoW-экстенты, отсутствие двойной истины для allocation и восстановление по ограниченному хвосту. Эти принципы приняты с корректировками, изложенными далее. Полный файл `aether-os-fs-contract.md` по указанному `/workspace/...` не был доступен в рабочей среде; использован **полный текст замечаний, вставленный в сообщение**, а также приложенный DOCX.

### 0.3. Соответствие текущей IntellectOS

Фактический код IntellectOS уже имеет собственные UEFI/BIOS-загрузчики, BootInfo ABI v1, x86-64 Memory Core M1, локально протестированные M2 Kernel Heap и C1 COM1-монитор. **Пока нет** полноценного дискового драйвера, VFS, пользовательских процессов, изоляции адресных пространств, IVX Loader и системного демона хранения. Сначала IntellectFS реализуется как **host-side формат, библиотека, валидатор, mkfs и набор crash-тестов**; в ядро интегрируется после наличия корректного BlockDevice API и защиты памяти. BootInfo v1 **не изменяется**.

### 0.4. Обязательные правила, которые нельзя ослаблять ради скорости

1. Никогда не перезаписывать живые данные или живой узел метаданных *на месте*.
2. Никогда не публиковать корень, указывающий на незаписанные либо непроверяемые байты.
3. Не выдавать подтверждение `POWER_FAIL` до подтверждения установленного протокола барьеров; если устройство не предоставляет достоверных гарантий — `DURABILITY_UNSUPPORTED`, а не фиктивное `PASS`.
4. Никогда не использовать один и тот же физический блок одновременно для двух достижимых несовместимых версий.
5. Недостижимая новая запись допускается как мусор; достижимая битая запись не выдаётся как успешное чтение.
6. Прежде чем освободить предыдущий корень, обеспечить закрепление всех ещё необходимых версий: открытые читатели, снапшоты, recovery checkpoint, IVX-маппинги.
7. Персистентные структуры имеют один определённый источник истины — **достоверно опубликованный корень и подчинённые ему CoW-структуры**. Кэши, компактные индексы и битмапы не являются вторым источником.
8. Не смешивать «проверку наличия хеша» с защитой от злонамеренного rollback: от подмены на старый валидный корень нужен независимый якорь доверия.
9. При повреждении обязательной структуры — отказ монтирования RW или деградация RO; никакого восстановления путём подстановки нулевых данных.
10. Все внешние байты — недоверенный ввод, в том числе дескрипторы устройства, каталог, журнал, IVX-файл и метаданные суперблока.

## 1. Модель и границы первой версии

### 1.1. Сущности

| Сущность | Назначение | Устойчивый идентификатор |
|---|---|---|
| `Volume` | Форматированный том на одном блочном устройстве/разделе | `volume_uuid: u128` |
| `Object` | Файл, каталог, симлинк, системный объект | `oid: u128` внутри тома |
| `DirectoryEntry` | Отображение имени на объект и его тип | `(parent_oid, name_bytes)` |
| `Extent` | Неизменяемая последовательность байтов файла | логический интервал + `IFSPointerV1` |
| `Shard` | Независимый домен индексов, аллокации и публикации | `shard_id: u32` |
| `Transaction` | Группа атомарно публикуемых изменений | `(writer_epoch, tx_id)` |
| `Seal` | Проверяемое свидетельство публикации нового состояния | `(writer_epoch, local_seq)` |
| `Snapshot` | Закреплённый корень неизменяемой версии | `(snapshot_id, root_refs)` |
| `Checkpoint` | Проверенная ограниченная точка восстановления | `checkpoint_seq` |
| `Handle` | Право доступа к объекту процесса | непередаваемый сырой индекс ОС + поколение |

### 1.2. Утверждённые границы `IFS-1`

- 64-битная адресация и 4-КиБ базовая единица дискового формата; в первой реализации x86-64 little-endian.
- Один **активный владелец RW-тома** в каждый момент; несколько процессов и CPU могут одновременно инициировать операции через него. Многохостовые RW-монтажи и CXL кооперация не входят в v1.
- Один или несколько локальных шардов; v1 не требует онлайн-переразбиения шардов. Перемещение объекта между шардами — явная транзакция и/или операция миграции.
- Прямые пользовательские права доступа к NVMe Submission/Completion Queue не даются без IOMMU/capabilities и строгого посредника ОС; первый драйвер — обычный доверенный драйвер BlockDevice.
- Файлы, каталоги, симлинки, hardlinks для обычных файлов, sparse extents, CoW snapshots, reflink, checksummed reads, ограниченные atomic rename.
- Не обещаются native RAID5/6, dedup всего тома, CXL, распределённые снимки, пользовательские запросы eBPF внутри диска или постоянная работа без fsck. Для каждого отдельного опционального механизма обязателен feature gate и новые тесты.
- Системный ESP UEFI остаётся в FAT на ранней стадии. IntellectFS — корневая/пользовательская ФС после того, как ядро научится читать блоки. Формат загрузочных байтов EFI не меняется.

### 1.3. Цели, а не вымышленные достижения

Объект оптимизации — вектор `latency(p50,p99,p99.9) + throughput + CPU/IOPS + RAM/op + WAF + recovery_time + corruption_detection`. Нельзя обещать «быстрее всех ФС» без одинакового железа и профиля. На одиночном SATA SSD пользовательские транзакции `POWER_FAIL` могут быть гораздо медленнее, чем `VOLATILE`. На HDD последовательное размещение может значить больше, чем сложный параллелизм; конфигурация выбирается по реальным измерениям.

## 2. Модель блочного устройства

### 2.1. `BlockDeviceV1`

Контроллер представляется не как «надежный диск», а как устройство с явно объявленными и проверенными возможностями:

```text
capacity_bytes(): u64
logical_sector_bytes(): u32
physical_sector_bytes(): Option<u32>
read(offset, len, buffers) -> Completion
write(offset, len, buffers, flags) -> Completion
flush(scope) -> Completion
trim(offset, len) -> Completion [optional]
capabilities() -> DeviceCapabilitiesV1
reset()/reconnect() -> status
```

`read`, `write`, `flush` должны проверять overflow, выравнивание, границы, отмены, таймауты, повторные и частичные завершения. Механизм DMA использует только разрешённые и закреплённые страницы, а устройство не имеет доступа к произвольной памяти ядра. Неопределённая ошибка завершения WRITE означает **неизвестность** результата на физическом уровне; драйвер обязан сверить или отбросить незафиксированную версию, не подтверждая успех наугад.

### 2.2. Обязательный профиль `SAFE_BLOCK_V1`

Предполагается, что устройство корректно: (а) читает ранее подтверждённые энергонезависимые данные; (б) выполняет подтверждённый `FLUSH`/FUA согласно контракту; (в) не записывает произвольно в LBA, не участвовавшие в операциях; (г) сообщает необратимые ошибки или даёт неверные байты, которые обнаружит хеш; (д) ограниченно рвёт **записываемые** блоки при обрыве питания. Нельзя считать поддержку (а)–(в) истинной для неисправной прошивки. Простая проверка IDENTIFY не доказывает поведение при реальном питании.

`PERSIST_ACK_CAPABLE` включается, только если storage policy допускает этот путь. Для неизвестного USB-флеш-накопителя разрешается RW best-effort с явным уровнем `ORDERED`, либо RO; нельзя маркировать подтверждение как аппаратно проверенное.

### 2.3. Нельзя путать размер логического блока с атомарностью

`FS_BLOCK = 4096` означает формат адресации, checksum и выравнивание. Это **не** утверждение, что весь блок атомарен при power loss: реальное `AWUPF`, `NAWUPF`, sector size, NPWG и особенности FTL отличаются. Даже с поддержкой аппаратного atomic write путь IFS-1 по умолчанию использует CoW, проверки и независимую резервную точку. Оптимизация AWUPF лишь выбирает меньше записей при явно доказанных условиях.

### 2.4. Классы I/O

- `READ_CRITICAL`: корневые метаданные, интерактивный ввод, IVX page-in.
- `WRITE_SEAL`: записи commit-descriptor/seal и финальные flush.
- `WRITE_SYNC_DATA`: пользовательская транзакция `POWER_FAIL`.
- `WRITE_BULK`: потоковые данные, БД, большие файлы.
- `GC_BACKGROUND`, `SCRUB_BACKGROUND`: ограниченная по бюджету работа.

Планировщик отделяет срочные маленькие I/O от bulk-потока, чтобы throughput не разрушал p99. Запросы, чья запись меняет корень, не могут обгонять обязательные барьеры данных.

## 3. Единый протокол транзакций и долговечности

### 3.1. Нативный примитив

```text
TxHandle fs_tx_begin(VolumeHandle v, TxOptions opt)
Result   fs_tx_mutate(TxHandle tx, Mutation m)
SealResult fs_tx_seal(TxHandle tx, DurabilityLevel level)
Result   fs_tx_abort(TxHandle tx)
```

`fs_tx_mutate` может создавать/удалять объект, записывать диапазон, обновлять размер, переименовывать запись, менять metadata/ACL, создавать hardlink, делать reflink, переключать namespace release pointer. **Имя, размер, данные, rights и ссылки — одна транзакция, если клиент включил их в один tx.** Нет обязательного дополнительного `fsync(dir)` для нативной атомарной транзакции. Один успешный вызов `write()` внутри tx **не** является свидетельством долговечности.

### 3.2. Три уровня

| Level | Видимость после `seal` | Что допускается после внезапной остановки | Требования к устройству |
|---|---|---|---|
| `VOLATILE` | Новое состояние немедленно видно по правилам MVCC в RAM | Вся транзакция может исчезнуть; старый опубликованный устойчивый корень остаётся корректным; никаких частично «появившихся» namespace-ссылок | Не требуется flush на путь подтверждения; фоновая физическая публикация проходит *обычный* data-first protocol |
| `ORDERED` | Новое состояние опубликовано, подготовлены устойчивые байты и корректный порядок | Если валидная печать сохранилась, все её данные должны быть доступны; сама печать может исчезнуть, и тогда используется предыдущее состояние | Устройство должно соблюдать pre-seal flush/order; seal не обязан быть подтверждён как durable |
| `POWER_FAIL` | Новое состояние опубликовано и печать запрошена как durable | После повторного монтирования выбранный корень содержит эту транзакцию либо более позднюю допустимую; **только при соблюдении устройства гарантий flush/FUA** | Успешные pre-seal и post-seal durable barriers; при отсутствии возможностей — ошибка, не понижение уровня |

`VOLATILE` никогда не означает «разрешено сбросить seal до данных без проверки». Он означает **RAM-only acknowledgement**, а физическая публикация делает обязательный порядок. При нехватке памяти грязные volatile состояния либо проходят background `ORDERED` commit, либо tx отклоняется; запрещена «эвакуация» видимого RAM-only namespace частично записанным seal. Для `ORDERED` успешный ответ не гарантирует сохранения самой печати. Если device вообще не способен дать достоверный **pre-seal flush**, IFS не имеет права физически публиковать новый seal как `ORDERED`: разрешены только RAM-only VOLATILE и RO, либо пользователь получает `IFS_E_NOT_DURABLE`. Для `POWER_FAIL` не достаточно вернуть success сразу после DMA write completion.

### 3.3. Atomic visibility и isolation

Внутри тома используется MVCC: читатель получает согласованное `read_epoch`, транзакция изменяет приватные CoW-объекты и публикуется в одной логической точке. Конкурирующие tx по одному `(oid, version)` проверяют конфликты через optimistic concurrency control. Независимые диапазоны одного файла допускают параллельную подготовку; обновление `eof`, link count и имени проходит явный conflict check. При повторных abort/starvation выполняется справедливый serialized fallback по ключу объекта/шарда, а не бесконечный OCC retry.

### 3.4. Машина состояний

```text
NEW -> RESERVED -> MUTATING -> VALIDATED
    -> DATA_ISSUED -> DATA_PERSIST_BARRIER_OK
    -> DESCRIPTOR_PERSISTED -> SEAL_ISSUED
    -> [SEAL_PERSIST_BARRIER_OK] -> ACKED

on failure before valid seal: ABORTED / ORPHANS
on ambiguous I/O: RECOVERY_REQUIRED; do not fabricate success
on post-seal ACK loss: client must query transaction ID
```

Параллельное физическое распределение данных допускается; **на публикацию состояние должно иметь однозначный последовательный порядок в пределах домена транзакции**. Seal writer — единственный компонент, который имеет право физически писать тип `IFSSealV1`; другие службы подают ему валидированные предложения.

### 3.5. Порядок для записи `POWER_FAIL`

1. Check ACL/capability, quota, locks, tx budget, writer fencing.
2. Резервировать **до начала работы** data blocks, metadata blocks, журнал/seal slots, snapshot/pin overhead, GC emergency reserve, hash-буферы. Переполнение/ENOSPC — до публикации; позднее ENOSPC до success вызывает abort, а не частичный успех.
3. Создать новые неизменяемые данные и узлы вне достижимых старых корней.
4. Записать эти байты и проверить все I/O completion, ошибки checksum/ENC.
5. `FLUSH(data durability domain)` — barrier A. Успешное завершение только по контракту устройства.
6. Записать immutable `IFSCommitDescV1`, покрывающий новые корни, зависимости, аллокации, releases; если descriptor записан после barrier A — нужен отдельный ordering barrier B для descriptor.
7. Выделенный seal writer пишет новую `IFSSealV1` в неактивный slot; seal имеет криптографический digest и связь с предыдущей допустимой печатью.
8. `FLUSH(seal durability domain)` — barrier C. Только после него вернуть `POWER_FAIL` success.
9. Старые корни и экстенты освобождаются **позже**, когда удалены все pins и сохранена независимая безопасная recovery-версия.

Барьер A не заменяет барьер B, если commit descriptor создаётся после A. В реализации можно объединить A+B одним flush **после записи данных и descriptor, до записи seal**, потому что descriptor ещё никем не достижим. Это предпочтительный путь v1: `write(data + nodes + descriptor) -> flush -> write(seal) -> flush`.

### 3.6. Commit success, timeout и повтор

`SealResult` включает `tx_id`, `writer_epoch`, `shard_seqs[]`, `ack_level`, `durability_evidence`, `root_hash`, `status`. После таймаута клиент **не должен** повторять небезопасное создание под новым tx_id. Метод `fs_tx_status(tx_id)` возвращает `SEALED`, `NOT_SEALED` или `UNKNOWN`, а повтор того же tx_id идемпотентен, если payload hash совпадает; reuse tx_id с иным payload — `TX_ID_REUSE`.

После `POWER_FAIL` success, если устройство нарушило Flush и данных нет, IFS сообщает нарушение контракта и событие потери устойчивости; не исправляет историю фразой «прошёл тест».

### 3.7. POSIX-совместимость

Позднее POSIX-шлюз реализует `open/write/rename/fsync/fdatasync`, но **точные гарантийные границы описываются отдельно**. `close()` по умолчанию не синоним `POWER_FAIL seal`. Для корректной замены конфигурации native API предусматривает `tx_begin -> create tmp -> write -> set rights -> rename -> seal(POWER_FAIL)` — одна операция долговечности, без последовательности двух недокументированных `fsync`. POSIX-шлюз не обещает тождественности ext4 и не считает успех `write()` долговечным.

## 4. Инварианты достижимости и защитная модель отказов

**R1. Seal atomicity by validation.** После crash parser выбирает только запись с допустимыми magic/version, CRC, full digest, правильными UUID, epoch, slot, цепочкой и доступным descriptor. Рваную печать отвергает. Не предполагается физическая атомарность 4096 байт.

**R2. Complete reference.** Каждый достижимый immutable extent имеет корректную длину, диапазон, тип и связанный с его физическим местом hash/tag. Повреждение не превращается в нули и не скрывается; вернуть `EIO_CORRUPT` / использовать достоверную реплику.

**R3. No name before data.** Новое имя и его `oid`, размер и extents публикуются в одной достижимой версии. Старые имена не могут после crash указывать на незаписанные новые байты при соблюдённом порядке Flush.

**R4. No live/free overlap.** Ни один блок, достижимый из любого закреплённого корня, не присутствует одновременно в доступном free-set. Проверка относится также к старому checkpoint, snapshot, IVX mapping и транзакциям pre-seal.

**R5. Orphan != data loss.** Незапечатанные байты становятся недостижимыми orphan allocations; их последующий GC допустим. Они никогда не используются как источник состояния namespace.

**R6. No forged success.** Ошибка контроллера или недоказанная durable capability не превращается в `POWER_FAIL=SUCCESS`.

**R7. All roots typed.** Тип/поколение/UUID/положение/хеш каждого корня проверены; арифметические и циклические ошибки любого уровня приводят к fail-closed.

**R8. No rollback masquerade.** Старый корректный root cryptographically valid, но не эквивалентен актуальному root. Для защиты от злонамеренного отката требуется внешний доверенный monotonically advancing anchor; его отсутствие явно отражается в mount security status.

**R9. Writer epoch exclusive.** RW-монтирование требует уникального durable epoch/fence. После подозрения на параллельного писателя — RO без права продолжать транзакции.

**R10. Recovery idempotent.** Любая последовательность `recover -> crash -> recover` даёт тот же либо более новый корректно запечатанный state без double-free и двойного применения мутаций.

### 4.1. Failures, которые моделируем обязательно

- отключение питания между любыми двумя WRITE и FLUSH, внутри многосекторной WRITE и внутри любой 4-КиБ записи;
- reorder и partial completion для независимых команд до barrier;
- потеря I/O completion при фактически выполненной записи;
- bit flip данных, метаданных, журнала, anchor и обеих копий bootstrap;
- неверный LBA и старый блок на ожидаемом адресе;
- заполнение тома, исчерпание log slots, crash во время GC и reclaim;
- неожиданная смена writer epoch, двойное монтирование, переполнение счётчика;
- stale device geometry, trim discarded-live-block, исчезновение устройства;
- отложенный отказ RAM/DMA/CPU, отдельный от модели физического накопителя;
- «lying flush» как **негативный эксперимент**: тест должен показать предел гарантий и по возможности обнаружить нарушение, но не обещать математически невозможную устойчивость.

### 4.2. Гарантии и отказ от гарантий

Контрольные хеши выявляют случайные повреждения с чрезвычайно высокой вероятностью. Без зеркала/backup ФС **не может восстановить** единственную повреждённую копию. Криптографический хеш без внешне аутентифицированного корня **не предотвращает злонамеренную подмену всего дерева**. Снимок не является резервной копией от физического отказа того же SSD. Ни CoW, ни формальные доказательства алгоритма не спасают от произвольной порчи всех LBA контроллером.

## 5. Дисковое адресное пространство и геометрия тома

### 5.1. Физическая единица

`IFS_BLK = 4096` байт, блок адресуется `pblk: u64` относительно начала раздела IntellectFS, не физического NVMe namespace. Все on-disk u16/u32/u64 — **little-endian**, незнакомые обязательные flags отвергаются. `volume_blocks = floor(volume_bytes / 4096)`; хвост меньше блока недоступен. Все `offset + length` через checked arithmetic в u128, затем сравнение с geometry; никакого integer wrap. Сегменты длиной ноль допустимы только для документированных zero-data записей и hole; указатель на 0-й блок никогда не является валидным allocated extent.

### 5.2. Постоянные области

```text
partition block 0       : reserved / invalid access sentinel
partition block 1,2     : bootstrap A/B
partition block N-3,N-2 : bootstrap C/D
partition block N-1     : reserved end guard
fixed front reserved    : anchor/checkpoint/seal ring, writer-fence records
fixed per-shard regions : seal rings + emergency metadata reserves
remaining blocks        : CoW data extents + CoW metadata nodes
```

В реальном layout ring области задаются bootstrap и обязаны быть **непересекающимися**; геометрия вычисляется `mkfs` с детерминированным алгоритмом, проверяется mount и fsck. **Таблица расположения шардовых колец** хранится в immutable `IFSLayoutManifestV1`, чей хеш и адрес выводятся из последнего достоверного *глобального* descriptor/seal (не из `shard_manifest_hint_pblk`). Начальная глобальная цепочка доступна по fixed `anchor_first_pblk`; только после её проверки разрешено читать local shard rings. Некорректный manifest блокирует RW. Так разрывается «курица-и-яйцо» определения местонахождения локального журнала при восстановлении. Два конца тома защищают от частичного повреждения первых/последних блоков, но не от полной потери устройства.

Минимальный размер тома IFS-1: **256 МиБ**; число блоков не менее 65536; диапазон, заполнение и расположение журналов рассчитываются из этого ограничения. Нельзя размещать footer за пределами устройства или пересекать GPT (границы здесь уже **внутри partition**, а не всего disk).

### 5.3. Области размещения

- `boot reserve`: superblock/anchor/fence, выделяется mkfs и никогда не попадает в пользовательский аллокатор.
- `metadata reserve`: bounded pools для замены деревьев и аварийных checkpoint.
- `normal`: data/metadata с локальностью горячих/холодных записей.
- `recovery reserve`: защищённый запас для завершения уже начатых commits и восстановления; **не** доступен обычным `write`.

Начальный профиль: `reserve_min = max(5% capacity, 64 MiB)` для тома, когда геометрия допускает; при малом томе min-процент/абсолютная величина выбирается так, чтобы оставался полезный объём, и константы корректируются mkfs policy. Вводится явный `reserve_policy` в bootstrap. Целевые предупреждения `85%` и `90%` — настраиваемая политика производительности, не форматный критерий корректности.

`bootstrap_digest = BLAKE3("IFS/bootstrap/v1\0" || entire_4096_block_with_bytes_128_to_159_zero)`; точную последовательность доменного текста кодировать ASCII с завершающим `0x00`, без length-prefix. Дайджест **не подписывает** volume против злонамеренного SSD. Все резервные байты MUST быть нулевыми в v1. Алгоритмы SHA/BLAKE требуют отдельного нормативного golden vector до freeze.

### 6.2. Выбор bootstrap

Читаем все четыре фиксированные копии. Валидируем geometry, checksum, feature bits, ring overlap и UUID. Из допустимых выбираем максимальную **согласованную** generation, но не объявляем корень опубликованным только по bootstrap. В случае расхождения UUID среди копий RO / `FS_BOOTSTRAP_SPLIT_BRAIN`. Смена generation происходит CoW-style: пишем старшую неактивную копию, flush, затем вторую; не переписываем все копии одновременно. Две старые копии сохраняются до подтверждения новой checkpoint цепочки.

### 6.3. Fence epoch

Перед разрешением нового RW writer безопасный mount публикует `IFSSealV1(kind=WRITER_FENCE)`, с `writer_epoch = max_valid_epoch + 1`, проходящий уровень `POWER_FAIL`; проверяет, что старый writer остановлен/отфенсирован. Значение присутствует в запечатанных anchor-records и периодически закрепляется в `writer_epoch_floor`. **Нельзя** полагаться только на поле bootstrap с возможной старой копией; действующий writer epoch определяется цепочкой допустимых записей. RW на блочных устройствах, одновременно доступных двум машинам без внешнего fencing, запрещён даже при корректных checksums. В частности, если восстановление видит оборванную или противоречивую цепочку fence-epoch после последнего известного high-water mark, оно **не** понижает безопасно epoch до старого значения, чтобы продолжить RW: нужна новая независимая fence-публикация, а при неопределённом распределённом ownership — RO. Для шифрования обязательно предотвращать reuse nonce после каждого допускаемого recoverable crash.

### 7.1. Поля

| 44 | 4 | `reserved0` | 0 |

| 80 | 8 | `descriptor_pblk` | immutable commit descriptor location |
| 88 | 4 | `descriptor_blocks` | 1..256, кроме `WRITER_FENCE` = 0 |
| 92 | 4 | `descriptor_format` | `1` для tx/checkpoint; 0 для fence |
| 96 | 32 | `descriptor_digest` | BLAKE3 descriptor bytes, zero для fence |
| 128 | 32 | `previous_seal_digest` | цепочка, учитывающая re-used ring slots |
| 160 | 32 | `root_summary_digest` | проверяемое короткое summary публикации |
| 192 | 8 | `fence_epoch` | совпадает с writer_epoch для WRITER_FENCE; иначе 0 |
| 200 | 8 | `record_slot` | ожидаемая физическая позиция внутри ring |
| 208 | 4 | `crc32c` | быстрая проверка torn/random corruption |
| 212 | 4 | `hash_alg_id` | `1` = BLAKE3-256 |
| 216 | 32 | `seal_digest` | BLAKE3 отдельный domain |
| 248 | 8 | `reserved1` | 0 |
| 256 | 3840 | `padding` | 0 |

Сначала вычисляем `seal_digest = BLAKE3("IFS/seal/v1\0" || 4096 bytes, где поля crc32c и seal_digest обнулены)`. Затем вычисляем CRC32C по 4096 bytes с обнулённым **только** полем `crc32c`; записываем его в offset 208. Для проверки сначала CRC, затем digest. CRC32C означает **Castagnoli**, reflected polynomial `0x82F63B78`, init `0xffffffff`, final XOR `0xffffffff`, без скрытой привязки к аппаратному ускорителю; byte stream включает все 4096 байт с четырьмя обнулёнными байтами CRC. CRC — ускоритель отсева, **не** защита от противника. Нельзя вычислять `seal_digest` по самосодержащемуся байту без zero-exclusion.

### 7.2. Семантика seal как «логически атомарной публикации»

Физическая запись может быть разорвана на любом байте; читатель принимает **либо целиком согласованную запись, либо её не существует**. Вероятность случайного torn блока с корректным криптографическим хешем мала, но нельзя выдавать это за защиту от скомпрометированного writer/ключа. Устройство не обязано атомарно записывать seal. Несколько независимых slots и сохранённый checkpoint позволяют пережить частичную запись без повреждения предыдущей версии.

### 7.3. Ring и подтверждённая старая версия

Slot перезаписывается **только если** он не содержит последнюю необходимую recovery-anchor-версию и у него нет active pin. Селектор ring учитывает physical slot + generation, что исключает ABA. После достижения безопасного checkpoint запись старого журнала может быть освобождена по reclaim frontier; до этого её перезапись запрещена. Сокращение recovery tail не может уменьшать окно между действующим commit и последним подтверждённым checkpoint до нуля. При checkpoint rotating commit chain, `previous_seal_digest` в новом initial record связывается с digest финального защищённого anchor старой эпохи; переход через anchor фиксируется явным `CHECKPOINT` descriptor, а не догадкой по максимальному числу seq.

### 7.4. Чего не делает seal

Она не хранит большие пользовательские данные, не выполняет произвольный код, не разрешает unsafe in-place patch, не удостоверяет identity автора, не содержит приватные ключи, не является единственным источником полномочий и не даёт право восстановить повреждённые bytes без избыточности.

## 8. Commit descriptor и единственный источник истины

### 8.1. `IFSCommitDescV1`

Это неизменяемая бинарная запись из 1..256 блоков, каждый блок проверяется общей `descriptor_digest` seal. Стандартный descriptor-encapsulation:

```text
[0:8]    magic = "IFSC0001"
[8:10]   version = u16(1)
[10:12]  header_bytes = u16(128)
[12:16]  total_bytes = u32 (>=128, <= 1 MiB)
[16:24]  writer_epoch = u64
[24:32]  tx_id = u64
[32:40]  commit_generation = u64
[40:56]  volume_uuid = 16 bytes
[56:88]  body_digest = BLAKE3("IFS/commit-body/v1\\0" || body bytes)
[88:120] previous_root_digest = BLAKE3-256
[120:128] reserved = zero
[128:total_bytes] canonical ordered TLV body
[total_bytes:pad_to_4096] zero
```

`descriptor_digest = BLAKE3("IFS/commit-desc/v1\0" || exact_padded_descriptor_bytes)`. Внешний seal обязан совпадать с descriptor epoch/tx_id и root summary. TLV body сортируется по `(tag, key)`; integer — fixed LE; TLV length/offset обязаны укладываться в total_bytes; дубликат singleton tag — reject; неизвестный mandatory tag — reject, optional tag — только по feature policy.

**Обязательные TLV группы:** `ROOT_SET`, `OBJECT_EPOCH`, `ALLOCATION_ROOT`, `ALLOCATION_DELTA`, `RELEASE_QUEUE_ROOT`, `SNAPSHOT_ROOT`, `CROSS_SHARD_PARTICIPANTS` (когда нужно), `QUOTA_DELTA`, `REQUEST_HASH`, `POLICY_REVISION`, `RECOVERY_FRONTIER`. `ROOT_SET` содержит `{shard_id -> [object_tree_ptr, dir_tree_ptr, extent_tree_ptr]}`; `ALLOCATION_ROOT` — единственный CoW-подчинённый корень свободного пространства данного состояния. Служебные битмапы и кэши **не** могут «поправить» противоречащий seal root.

### 8.2. Почему аллокатор не является второй независимой истиной

Free-space index — **часть того же опубликованного root-state**, а не синхронизируемый отдельно bitmap. В нём учитываются allocated метаданные, включая новые узлы самого allocation-tree. Чтобы избежать циклического выделения, tx preflight вычисляет консервативную верхнюю границу новых allocation-tree nodes, заранее резервирует адреса в рабочем наборе (до записи), затем строит дерево bottom-up. Конечный self-accounting лист может помечать местоположение своего узла allocated — это **не криптографический цикл**, поскольку этот лист не хранит свой собственный hash. После seal смета и фактические allocation bits однозначно выводятся из committed root и delta. Неиспользованные резервы возвращаются в новую версию free-set до построения окончательного descriptor.

При сбое до seal временные резервы не принадлежат опубликованному дереву. Они могут оказаться неиспользуемыми orphan blocks до reconciliation. Проверка `fsck` сравнивает allocated граф (плюс pinned roots и служебные fixed regions) с опубликованным free-set; если пересечение — RO/repair candidate, никогда RW на сомнительных блоках.

### 8.3. Что считается источником истины после crash

Только `valid bootstrap -> valid ring checkpoint/fence -> valid seal chain -> valid commit descriptor -> valid root pointers -> reachable immutable nodes`. RAM cache, Bf-mini-pages, свободные bitmaps, вторичные reverse maps и журнал запуска процессов восстанавливаются из этого состояния. Read-only fsck не должен менять исходный том, пока не получено явное подтверждение repair.

### 8.4. Размер транзакции и bounded work

`IFSCommitDescV1` ограничен 1 МиБ, и обычная транзакция имеет лимит по числу модифицированных nodes/allocated extents, задаваемый resource policy. Большие последовательные записи публикуются группами, если клиент не потребовал больший атомарный batch; тогда он получает `TX_TOO_LARGE` до частичного ack. Опасно обещать атомарность произвольных терабайт за один seal без зарезервированных журналов и без ограничения recovery.

## 9. Форматы указателей, блоков и индексов

### 9.1. `IFSPointerV1` — ровно 128 байт

| Offset | Bytes | Field | Значение |
|---:|---:|---|---|
| 0 | 8 | `physical_block` | начальный pblk данных |
| 8 | 4 | `physical_blocks` | число 4096-байтных блоков |
| 12 | 4 | `stored_bytes` | число действительно записанных байтов |
| 16 | 4 | `logical_bytes` | число байтов до сжатия |
| 20 | 2 | `flags` | INLINE запрещён для внешнего pointer; `ENCRYPTED`, `COMPRESSED`, `METADATA` и известные |
| 22 | 1 | `codec` | `0 raw`, `1 LZ4-block`, `2 Zstd` (опционально, feature gate) |
| 23 | 1 | `cipher` | `0 none`, `1 XChaCha20-Poly1305` (опционально) |
| 24 | 4 | `key_id` | идентификатор версии ключа, 0 без ENC |
| 28 | 8 | `birth_sequence` | версия создания immutable payload |
| 36 | 8 | `owner_oid_hi` | контекст владельца |
| 44 | 8 | `owner_oid_lo` | контекст владельца |
| 52 | 8 | `logical_offset` | смещение внутри объекта |
| 60 | 8 | `nonce_counter` | уникально зарезервированный IV при ENC; иначе 0 |
| 68 | 2 | `hash_algorithm` | `1 BLAKE3-256` |
| 70 | 2 | `block_kind` | `1 data`, `2 tree`, `3 descriptor-extension`, etc. |
| 72 | 32 | `payload_digest` | hash ниже |
| 104 | 16 | `auth_tag` | AEAD tag, zero без ENC |
| 120 | 8 | `reserved` | нули |

`payload_digest = BLAKE3("IFS/pointer/v1\0" || volume_uuid[16] || pointer_bytes[0:72] || pointer_bytes[104:120] || payload_bytes[0:stored_bytes])`. При чтении **обязательна** проверка `stored_bytes <= physical_blocks*4096`, размера, выравнивания, типа, full digest и, если есть, AEAD tag; у padding отдельное правило: все неиспользованные байты физического блока `MUST` быть нулями для v1 (zero-pad до encrypt, checksum рассчитывается только по `stored_bytes`, но при проверке читаются все блоки и padding сверяется с нулями). При шифровании `stored_bytes` относится к ciphertext, tag вне payload; AEAD AAD определяется ниже. При переносе блока на иной LBA pointer и его hash **обязательно** пересоздаются CoW, поскольку физический адрес входит в hash context.

### 9.2. `IFSNodeV1` — 4096 байт

```text
offset  size   field
0       8      magic = "IFSN0001"
8       2      version = 1
10      2      kind (OID_TREE, DIR_TREE, EXTENT_TREE, FREE_TREE, SNAP_TREE, etc.)
12      2      header_bytes = 96
14      1      level (0=leaf)
15      1      flags (v1=0)
16      8      owner_oid_hi
24      8      owner_oid_lo
32      8      birth_sequence
40      4      item_count
44      4      body_bytes (<=4000)
48      8      right_sibling_hint_pblk (optimization only, never authoritative)
56      8      reserved = 0
64      32     node_digest
96      N      canonical packed sorted records
96+N    ...    zero padding
```

`node_digest = BLAKE3("IFS/node/v1\0" || whole_4096_node_with_digest_field_zero)`; дополнительно **родительский `IFSPointerV1` проверяет и физическое расположение, и содержимое**. Для root pointer hash хранится в `IFSCommitDescV1`, поэтому цепочка проверяется до seal. Нельзя доверять `right_sibling_hint_pblk` без проверки того же поколения и полного пути; при неверном hint выполняется поиск от корня, а не опасный переход.

Записи сортируются по **байтам канонического ключа**, не по текущей локали пользователя. На уровне листа дубликат ключа — `FS_BAD_NODE`. На внутреннем уровне обязательны строгие границы диапазонов child pointers. Максимальная глубина задаётся `FS_MAX_TREE_DEPTH = 12`; циклы/повторное посещение во время проверки запрещены или учитываются через доказанное sharing. Depth-check нельзя отключать для производительности.

### 9.3. Представление record внутри node

```text
RecordV1 = [key_bytes:u16][value_bytes:u16][kind:u16][flags:u16]
           [key:key_bytes][value:value_bytes]
```

Вместимость — `96 + Σ(8 + key_bytes + value_bytes) <= 4096`. `key_bytes` и `value_bytes` проверяются до указателей. `kind` определяет сериализацию `value`, неизвестный обязательный kind отвергается. Внутренние separators используют `key_bytes` и ровно один 128-байтный `IFSPointerV1` как `value` плюс записанные диапазоны. Формат считается окончательно замороженным только после исполняемых golden vectors, включая big/small keys, Unicode bytes, disjoint extents и ошибки краёв.

### 9.4. Деревья и индексы

- `OID_TREE`: `(oid) -> ObjectRecordV1`.
- `DIR_TREE`: `(parent_oid, name_raw_bytes) -> DirRecordV1`.
- `EXTENT_TREE`: `(oid, logical_start) -> DataExtentV1`.
- `FREE_TREE`: `(allocation_group, pblk_start) -> free_span_length`.
- `SNAP_TREE`: `snapshot_id -> pinned root set`.
- `RELEASE_TREE`: отложенные освобождения, epoch frontier.
- `QUOTA_TREE`: usage/reservation по субъектам.
- `XATTR_TREE`: расширенные атрибуты с ограниченным размером.

Первый подтверждённый экземпляр может использовать **обычное компактное CoW B+Tree** с фиксированными 4-КиБ nodes. Bε-дерево с буферизированными апсертами, Bf-министраницы и компрессия индекса являются **эволюцией внутреннего алгоритма** без изменения внешней модели объектов; изменение on-disk node kind требует feature flag, независимого валидатора и migration policy (не молчаливое изменение магического блока).

### 9.5. Маленькие объекты и большие байты

Малые данные до **256 байт** в `ObjectRecordV1` могут храниться inline (в пределах node capacity); настраиваемый предел расширения до 1024 байт исследуется отдельно. Нельзя вкладывать в Bε-узел десятки/сотни KiB пользовательских данных. Свыше inline порога используется внешнее размещение в immutable extents; базовые предпочтительные sizes для SSD: 4/16/64/256 КиБ, но верхняя граница extents при v1 устанавливается политика+лимитом pointer `physical_blocks` и I/O budget. Sequential streaming получает larger contiguous extents; случайная 4-КиБ запись не переписывает неизбежно 1-МиБ горячий extent без subextent/splitting.

## 10. Объекты и пространство имён

### 10.1. OID

Внутри тома `oid` — 128 бит: `writer_epoch:u64 || object_sequence:u64` (LE wire). Номер объекта монотонен в рамках writer epoch, а epoch резервируется durable WRITER_FENCE перед первой записью. Уникальность across volumes обеспечивается парой `(volume_uuid, oid)`. Номер OID никогда не переиспользуется в пределах одного epoch; переполнение object_sequence — `EOVERFLOW`, не wrap. Копирование на другой том создаёт новый OID; rename и hardlink — сохраняют OID.

### 10.2. `ObjectRecordV1` (логическая схема)

```text
volume_uuid:u128 (implicit volume context)
oid:u128; type:u8 (FILE/DIR/SYMLINK/DEVICE_META)
object_generation:u64; metadata_version:u64
mode:u32; owner_principal:u128; group_principal:u128
capability_policy_id:u128; link_count:u64
logical_size:u64; allocated_bytes:u64
parent_oid:u128 (ONLY for directory; root parent=self)
extent_root:IFSPointerV1; xattr_root:IFSPointerV1
birth_tx:u128; change_seq:u64
ctime_ns:i64; mtime_ns:i64; atime_ns:i64 (wall clock ONLY metadata)
inline_bytes[0..256]; flags; checksum/context
```

Это **логическая** схема: поля имеют строгие типы и семантику; её TLV/packed size подлежит golden vectors перед freeze. В отличие от boot/IVX фиксированных структур, запись `ObjectRecordV1` не обязана быть фиксированного размера, пока сохраняется однозначная сериализация и enforcement.

### 10.3. Каталог — индекс, не путь

Ключ `(parent_oid, raw_name_bytes)`; `name -> oid`, `name` не часть идентичности. Переименование каталога внутри одного шарда изменяет entry и `parent_oid` каталог-объекта, но **не** переписывает ключи всех потомков. Контроль отсутствия циклов parent graph делается при move; hardlinks каталогов в v1 запрещены; root нельзя переименовать. При переносе root каталога между шардами применяется explicit cross-shard protocol.

### 10.4. Имена файлов

Имена — последовательности байтов длиной **1..255**, запрещены `0x00` и `/` (`0x2f`). `.` и `..` — виртуальные специальные компоненты и не создаются как обычные записи. Ключ **case-sensitive**, **не требует Unicode NFC/NFD**. Для консоли GUI/CLI предлагается UTF-8 визуализация с escape-последовательностями для не-UTF8 байтов. Допускается отдельный user-space casefolded index, не заменяющий канонический raw-byte ключ. Нельзя тихо превратить `a` и `A`, NFD и NFC, разные байты в одно имя после обновления Unicode table.

### 10.5. Hardlink, symlink, remove и orphan

- Hardlink разрешён только обычным файлам одного тома, link_count обновляется в том же seal, что entry.
- Symlink хранит необработанные bytes target; разрешение требует bounded hop count (`MAX_SYMLINK_HOPS=40`) и не может обходить capability sandbox.
- При удалении последней ссылки объект остаётся alive, пока открыт handle или snapshot; затем отправляется в deferred-free после последнего reader pin. Открытый файл может продолжать читаться после unlink.
- Переименование существующего target — атомарная замена entry в одном tx; если target — непустой каталог, v1 возвращает ошибку согласно политике интерфейса.
- Два `(parent_oid,name)` не могут в одной версии ссылаться на `oid`, который уже помечен окончательно освобождённым.

### 10.6. Конкурентные операции namespace

Locks/granularity: shard -> directory OID -> object version -> logical extent range. Избегаем ABBA через канонический порядок `(volume, shard_id, oid, range_start)`. Чтения оптимистические с MVCC; изменение link_count и rename требует сериализуемого конфликта, а не локальной эвристики по пути. `lookup(path)` обрабатывает каждый parent step с проверкой права и версии, либо использует согласованный snapshot root; сырой путь не назначает полномочий.

## 11. Размещение, аллокация и профили нагрузки

### 11.1. Allocation groups и шарды

`allocation_group_blocks` задаётся mkfs; группы не пересекаются. Каждому shards назначается набор AG; один физический блок никогда одновременно не принадлежит двум шардовым allocators. Shard-local root/seal writers позволяют готовить независимые tx параллельно; записи в одного `oid` разрешаются по его shard ownership. **Произвольного выбора шарда только по каталогу недостаточно**: файл может сохраняться в прежнем shard после rename, запись хранит shard_id.

### 11.2. Планировщик выделения

Вход: `{bytes, alignment, lifetime_class, locality_id, tier, compression, durability_level, reserve_budget}`. Выход: зарезервированный список непересекающихся extents либо `ENOSPC` до commit. Проверка учитывает quota, pending tx, snapshot pins, last checkpoint, held IVX pages, GC reserve. Учитываем не только свободные пользовательские байты, но и худший случай дополнительных metadata/path-copy и journal slots.

Предлагаемые классы lifetime:

```text
SYSTEM_CRITICAL (root/index/journal)
EXECUTABLE_IMMUTABLE (IVX/IVL)
HOT_SMALL_RANDOM (db index, logs)
HOT_APPEND (journals, event streams)
WARM_GENERAL
COLD_LARGE (datasets, media)
SNAPSHOT_PINNED
GC_MOVING
```

Классы — policy hints; неизвестные значения не меняют правила восстановления. NVMe FDP RUH, ZNS, CXL и прочая аппаратная кооперация могут использовать классы при наличии support, но дисковый формат работает без них.

### 11.3. Large file streaming

При последовательном чтении асинхронная prefetch с bounded depth, выровненный request merging и page cache bypass по advisory hint. При последовательной записи — уплотнение contiguous extents, metadata clustering и batched seals. Large writes никогда не обязаны проходить через Bε node, copy whole file или через глобальный mutex журналов. Для сжатых extents допускается chunk-level re-encode с ограниченным read-modify-write и явным accounting WAF.

### 11.4. DB и журналы

- `append_reserve(oid, n)` атомарно резервирует непересекающийся logical offset в одном shard; durable EOF меняется вместе с содержимым по seal.
- `fs_write_at` двух писателей в непересекающиеся extents допускает одновременный data prep, но commit проверяет общий объектный metadata_version и merge без lost updates.
- `DIRECT_IO` требует alignment, которое сообщает device/FS, либо явный safe bounce path; нельзя выдавать in-place DMA доступ к CoW структурам.
- Для WAL-операций tx batch допускает `POWER_FAIL` с минимальным количеством Flush, но контракт не обещает стоимость одного flush менее возможностей SSD.

### 11.5. GC, WAF и резервирование

Garbage collector перемещает только live-экстенты по новым CoW-адресам, создаёт новый pointer/parent/root и публикует seal **до** освобождения старого. Скоростные пределы: `gc_cpu_pct`, `gc_iops_budget`, `gc_write_MBps`, `low_free_soft`, `low_free_hard`. При low reserve GC получает приоритет и замедляет новые writers, но не нарушает read/critical seals. По достижении emergency reserve новые обычные операции отвергаются `ENOSPC` до commit; fsck/repair имеют отдельный защищённый ресурс.

`WAF = physical media bytes written / logical application bytes committed` измеряется отдельно от internal SSD WAF (не всегда известен). Не рекламировать target 1.2 как гарантию без данных. При застарелой фрагментации применяется фоновое cold-placement refinement, а не полный online rebalance всего тома.

## 12. Хеширование, компрессия, шифрование

### 12.1. Integrity layer

Все metadata blocks **MUST** иметь BLAKE3-256 и родительский pointer hash. По умолчанию все пользовательские data extents **MUST** иметь BLAKE3-256, а не опциональный CRC-only. CRC32C применяется для быстрого short-circuit проверки seal/headers. Дайджест включает домен, volume UUID, physical location, тип, логический owner и bytes. Подмена между двумя файлами/offset/generation обнаруживается, если валиден доверенный родительский root.

### 12.2. Read order

```text
read physical bytes -> size / padding check -> pointer hash verify
-> encrypted? AEAD authentication/decrypt -> compressed? decompress
-> logical_size/offset/bounds check -> deliver clean data
```

Нельзя отдавать неподтверждённые bytes из cache или mmap с `success`, если политика обещает verified read. Для страниц executable IVX нужна **обе** проверки: IFS extent integrity и собственная подпись/корень IVX. Загрузка одного signed IVX не освобождает ФС от проверки extents, и один IFS hash не заменяет проверку IVX происхождения.

### 12.3. Компрессия

`codec=0` обязателен во всех реализациях v1; `codec=1` означает LZ4 **raw block** с точным declared uncompressed length, `codec=2` — Zstd с жёсткими memory/workspace limits и version-independent decode conformance. Включение 1/2 требует `required_features`/node feature handling и golden vectors. Нельзя декомпрессировать сжатую бомбу без `MAX_DECOMPRESS_BYTES` и per-IO квоты. Никаких больших произвольных allocation во время проверки metadata root.

### 12.4. Encryption and nonce safety

Шифрование v1-опционально, разработка начинается без него. Предпочитаемый алгоритм для **проектной** ветки — XChaCha20-Poly1305 с 192-битным nonce. Nonce выводится через KDF(domain `IFS/nonce/v1`) из `(volume_uuid, key_id, writer_epoch, durable_reserved_nonce_counter)`; счётчик выделяется **пакетами с подтверждённым `POWER_FAIL` reservation fence ДО любого использования**. Неизрасходованные значения после сбоя выкидываются; reuse nonce+key запрещён даже когда tx никогда не был запечатан. Если device не поддерживает сохранение nonce reservation или генератор адресов подозрителен, шифрованная запись блокируется, а не повторяет nonce. IVX content hash и шифрование ФС имеют независимые ключи/идентификаторы.

AEAD AAD: domain, volume UUID, `key_id`, owner OID, object offset, `birth_sequence`, `logical_bytes`, codec, logical object type. Перемещение ciphertext в другой физический LBA требует новый pointer digest, но необязательно новое шифрование, поскольку физический LBA намеренно **не входит в AEAD AAD**; такое перемещение всё равно защищено новой parent-pointer цепочкой, а не неподписанным адресом. Cross-owner encrypted dedup по умолчанию запрещён. Keys и revoke-list держатся **вне обычного snapshot namespace** в защищённой OS Key Service или sealed hardware store; в FS хранится только `key_id`/encryption policy. Заблокированный том не расшифровывается на основании одного superblock. **В v1 профиль `ENCRYPTED_DATA` защищает только содержимое data extents; имена файлов, часть размеров и другие метаданные остаются видимыми.** Полное шифрование метаданных потребует отдельного feature-flag и bootstrap-unlock/verification protocol, иначе нельзя честно обещать сокрытие namespace.

### 12.5. Защита от злонамеренного rollback

Локальные хеши и BLAKE3 digest позволяют обнаружить порчу при сохранном доверенном корне. Противник, переписавший весь том согласованным старым snapshot, может предъявить корректную цепочку. Для **authenticated volume** реализуется внешний `trusted_root_anchor`: signed/monotonic root token вне атакуемого тома, аппаратный защищённый счётчик либо независимая реплика с сильным соглашением. При отсутствии этого сервиса mount status `INTEGRITY_CHECKED_NOT_ROLLBACK_PROTECTED`; система не называет том tamperproof.

### 12.6. Отказ устройства и самовосстановление

При checksum mismatch: сначала bounded retry, затем независимая здоровая replica/mirror/snapshot backup по policy; после успешной проверки можно CoW-heal и seal. Без резервной копии — `EIO_CORRUPT`, quarantine и событие аудита. Ошибку нельзя лечить записью нулей, silent uncompressed fallback или выбранным «на глаз» older extent.

## 13. Snapshots, reflinks, pins, boot rollback

### 13.1. Снимки

Snapshot — immutable ссылочный набор корней с собственной `snapshot_id`, созданный seal-транзакцией. Операция создания snapshot одного шарда должна быть O(1) по объёму данных (внешние blocks не копируются), но bookkeeping/публикация могут стоить I/O и depth walk. **Не** обещаем строго O(1) для глобального multi-shard snapshot без координации.

### 13.2. Снимки всего тома

Глобальный snapshot требует остановить/согласовать публикации всех shards, durable cross-coordinator record и один `root_set`. Неполный/неподтверждённый глобальный snapshot не показывается клиенту после crash. Для первых версий допускается `SNAPSHOT_SCOPE=SHARD`, а глобальное API возвращает `ENOTSUP`, пока нет проверенного coordinator.

### 13.3. Reflink

Файлы могут разделять immutable extents через reference-pins. Первая запись в клонированный диапазон создаёт новый extent и новые ссылки CoW; нет shared in-place writes. Logical charged bytes и physical charged bytes учитываются раздельно. В качестве performance defaults устанавливаются `noatime` для Server/System профилей и `lazy-atime` для Desktop; wall-clock `atime` **никогда** не применяется как порядок устойчивых транзакций или recovery sequence. Не допускается misaccounting quota из-за двух владельцев одного data block. Если включено шифрование с AAD, привязанным к исходному `owner_oid`, **reflink между разными OID не может просто разделить тот же ciphertext**: безопасный путь v1 — re-encrypt под нового владельца с новым nonce и seal, либо `ENOTSUP`. Разделяемое шифрование с отдельным `content_scope_id` требует нового утверждённого профиля, не молчаливой оптимизации.

### 13.4. Open descriptors, mmap и IVX

Каждая активная операция чтения или memory-map pinned на `read_epoch`. Сменить имя `.ivx` или установить новую версию можно атомарно, но уже запущенный процесс сохраняет pinned страницы своего **исходного** executable content root. Перезапись исполняемой страницы по адресу в старом процессе запрещена. Запись user mmap в общем writable mapping допускается только по специальной coherency/transaction policy; первому релизу разрешено не поддерживать shared writable mmap.

### 13.5. System snapshots и update rollback

Снимок корневого системного набора `{kernel config, IVX installation closure, system service versions}` создаётся в одной политике обновления. Boot rollback проверяет подписи ядра, trusted root anchor и актуальные revoked keys **вне обычного снапшота**; откат на диск не должен автоматически откатывать защиту доверия. Удаление snapshot отсрочено до завершения всех связей и чтений.

## 14. Шарды, многопоточность и межшардовые операции

### 14.1. Шард в v1

В формате заранее объявлены `(shard_id, shard_root, allocated_AG_set, seal_ring_range, writer_epoch)`; шарды имеют непересекающиеся allocation groups и независимые `local_seq`. Один writer владеет всем томом, но может иметь N shard executors на разных CPU; никакого глобального mutex **на чтение или каждый user WRITE**. Общий serial point остаётся при cross-shard tx и редких volume checkpoints; считать, что его не существует, — ложное обещание линейного масштабирования.

### 14.2. Примеры параллельности

- Разные файлы в разных шардах: независимый I/O prepare, независимые normal seal rings.
- Два непересекающихся диапазона одного файла: parallel data prep, object version merge перед публикацией.
- `rename` внутри одного каталога / шарда: одно изменение directory index + link metadata, один seal.
- `rename` между каталогами разных shards: explicit `CROSS_COMMIT` с lock/fairness и coordinator; если off, `EXDEV`, а не двухфазное невидимое копирование.
- `link` между двумя shards: запрещён до cross-shard implementation.

### 14.3. Протокол multi-shard

1. Acquire participant fences в каноническом порядке shard ID, freeze только участвующие root generations.
2. Каждый shard формирует immutable prepared root and allocation deltas, но **не публикует** их как локально видимые текущие версии.
3. Write + persist всех data, metadata, participant descriptors; pre-seal barrier.
4. Publish один глобальный `IFSSealV1(kind=CROSS_COMMIT, shard_id=0xffffffff)` со ссылкой на coordinator descriptor с полным набором participants, roots, parent_seqs; post-seal barrier для `POWER_FAIL`.
5. При чтении shard root выбирать только version, разрешённую последним допустимым coordinator; до cross-seal prepared roots невидимы.
6. Crash before global seal: abort подготовку, предыдущие shard roots продолжают работать. Crash after global seal: apply all participant roots exactly once; когда участник физически отсутствует, mount RO/degraded и не выдаёт частичную rename.
7. Participant local seal chain может продолжаться только после завершения coordinator/fence, либо его continuation root обязан явно ссылаться на глобальный commit; orphan prepare не сливается с новыми локальными записями.

Данное условие делает cross-commit редкой дорогой операцией. Если опыт покажет, что она доминирует latency, надо менять placement policy, а не размывать атомарность.

### 14.4. Snapshot barriers vs user latency

Для консистентного global checkpoint coordinator публикует в одном immutable descriptor set of shard heads; shard seal rings продолжают существовать отдельно. Resume после checkpoint должен знать head каждого shard и state всех ранее принятых cross-commits. Периодические checkpoint не должны останавливать bulk I/O на минуты: допускаются short epoch barriers + асинхронная сборка COW checkpoint из pinned read epoch.

## 15. Memory cache, async I/O и API для IntellectOS

### 15.1. Два слоя кэша без двойной истины

`VerifiedDataCache`: key `(volume_uuid, pblk, birth_seq, payload_digest)`; хранит только успешно проверенные bytes и pin count. `ObjectIndexCache`: key `(oid, metadata_generation)`; ускоритель `OID_TREE`, `DIR_TREE`, `EXTENT_TREE`. Смена semantic generation инвалидирует только затронутые записи. Динамическое выделение RAM через PMM/VMM/KHeap не изменяет диск. Отключение питания теряет весь cache без потери устойчивого root.

### 15.2. Async interface

```text
fs_read_async(ObjectHandle, offset, iovecs, ReadOpts) -> Ticket
fs_write_async(TxHandle, ObjectHandle, offset, iovecs, WriteOpts) -> Ticket
fs_ticket_wait(Ticket, deadline) -> Completion
fs_tx_seal_async(TxHandle, durability) -> Ticket
fs_snapshot_create_async(VolumeHandle, scope) -> Ticket
fs_scrub_async(VolumeHandle, ScrubBudget) -> Ticket
```

Batching и zero-copy **не могут** bypass capability check, buffer pinning и verification. Контроллер не читает адреса пользователя без pinned IOMMU-safe buffer; if absent, используется copy/bounce. Completed tickets не подтверждают `POWER_FAIL` без final seal result.

### 15.3. Capability boundary

FS не доверяет строке пути как полномочию. Проверка `open` создаёт kernel-managed handle с `READ`, `WRITE`, `APPEND`, `LIST`, `CREATE`, `DELETE`, `RENAME`, `ADMIN`, `SNAPSHOT`, `RAW_BLOCK`, `EXECUTE_MAP` — минимально необходимыми правами. Изменение имени файла не меняет прав уже открытого handle сверх revocation model. `RAW_BLOCK` не выдаётся обычному IVX-процессу, тем более ИИ-агенту. ACL/owner metadata не может позволять syscall выйти за system capability container.

### 15.4. VFS integration

IntellectOS VFS реализует `Mount`, `Vnode`, `Dentry`, `FileHandle`, `PageCache`, `MountNamespace`. IFS engine — backend под VFS, а не второй namespace system. Root mount доступен до запуска shell по минимальной доверенной последовательности: Внутренний `ObjectHandleV1` несёт `{volume_uuid, shard_id, oid, object_generation}`. Запись каталога (`DirRecordV1`) содержит `target_shard_id`; поэтому открытие объекта по пути не требует глобальной блокируемой таблицы `oid -> shard`, а прямое `open_by_oid` без shard требует отдельного защищённого locator или возвращает `EINVAL`.  `driver -> block enumerate -> read-only IFS verify -> launch init service -> switch RW after fence/recovery`. Runtime loader получает inode/object handles, подтверждает IVX identity, затем выполняет secure map.

### 15.5. Консоль и серверная редакция

Терминал/Serial C1 существует раньше ФС. После user mode появятся `mount`, `ls`, `cat`, `cp`, `mv`, `rm`, `df`, `snapshot`, `scrub`, `fsck`, `stat`, `blockdev`, `ifsctl` как обычные подписанные `.ivx` команды. Server Edition должна монтировать том и работать headless без framebuffer; до этого ранний boot всё ещё имеет известную зависимость UEFI Stage E от GOP. Открывать доступ по сети до file permissions и process isolation запрещено.

## 16. Персистентные ключи, безопасность и доверие ОС

### 16.1. Области полномочий

```text
Kernel storage ABI / memory protection
     ↓ trusted IPC
IFS mount manager (single writer fencing)
     ↓ validated immutable transactions
IFS state engine / seal writer
     ↓ restricted BlockDevice driver
NVMe / AHCI / virtio-blk
```

В первой безопасной версии IFS engine может быть частью доверенного ядра, если user-mode capability isolation ещё не завершена, но **API и формат уже спроектированы так, чтобы позднее вынести сервис в отдельное защищённое адресное пространство**. Нельзя приписывать текущему ядру уже существующую изоляцию сервисов.

### 16.2. Угрозы

- Ошибки парсера/overflow/out-of-bounds/corrupt B+tree.
- Проблемы внезапного питания и недобросовестный контроллер.
- DMA corruption или сбой памяти.
- Злонамеренный непривилегированный IVX-процесс.
- Компрометация монтирующего администратора (не решается одним хешем ФС).
- AI prompt injection через содержимое файла (ИИ-служба не получает fs admin capability автоматически).
- Rollback, подмена snapshots/ключей, подстановка устаревшего signed IVX.
- Side channels sharing/dedup encrypted data.

### 16.3. Безопасность формата

Проверка каждого поля выполняется **до выделения потенциально огромного буфера**. Нулевой размер, большой count, выведенный из байтов пользователя pointer, огромная глубина, список с циклом, неизвестные mandatory features, overlap reserved blocks, неправильные padding и неверные sha/BLAKE3-domain — отказ. Верификатор имеет лимит `max_nodes`, `max_bytes`, `max_depth`, `max_wall_time` и никогда не исполняет пользовательский код/IVX во время проверки ФС.

### 16.4. Секреты

Private keys, recovery seeds, revocation authorities и anti-rollback tokens не пишутся в ordinary files под тем же снимком, который они авторизуют. Пользовательские backup keys могут храниться в OS key service, аппаратном TPM, смарткарте или независимом бэкапе, но root unlock не должен требовать исполнения непросмотренного `.ivx` из ещё не проверенного тома.

## 17. Crash recovery и fsck

### 17.1. Mount sequence — строгий порядок

1. `blockdev` обнаруживает реальную geometry; mount не доверяет прежнему sector size.
2. Читает четыре bootstrap-копии по фиксированным 4-КиБ адресам, проверяет digest и geometry.
3. Read-only scan ограниченных anchor/checkpoint areas; выбирает valid root-head и writer fence.
4. Проверяет journal chain после checkpoint, включая slot/gen/digest/descriptor и cross-shard coordinator.
5. Для кандидата нового root в режиме offline bootstrap делает bounded verification необходимых root nodes/descriptor path; для гарантированного обнаружения порчи всего пользовательского дерева позже нужен scrub, а не pretended full validation при mount.
6. Выбирает самый новый **доказуемо пригодный опубликованный root** и фиксирует known frontiers; не подменяет повреждённые extent data нулями.
7. Reconstruct allocator reservations, pending release queue, cached indices и orphan quarantine без повторных неидемпотентных frees.
8. Если requested RW: проверить exclusive writer, bump+durable writer epoch, проверить device durability status; иначе остаётся RO.
9. Запускает background scrub/GC только после успешного API mount.

### 17.2. Не существует универсального «мгновенного восстановления»

Если checkpoint и seal tail доступны, обычное восстановление ограничено размером tail, а не объёмом пользовательских файлов. Но повреждённая корневая структура, потеря allocator tree или полный режим `fsck --deep` могут требовать O(число живых блоков). Слова «восстановление всегда пропорционально грязному хвосту» недопустимы как абсолютная гарантия.

### 17.3. Состояния восстановления

`CLEAN`, `NEEDS_REPLAY`, `RECOVERED`, `DEGRADED_RO`, `CORRUPT_ROOT`, `SPLIT_BRAIN`, `UNSUPPORTED_REQUIRED_FEATURE`, `NO_DURABILITY_BACKEND`, `QUARANTINED`, `REPAIR_CANDIDATE`. Пользователю сообщается конкретный stage, offset, ожидаемый digest, фактический digest, seq, безопасное действие. Ни один `fsck` не принимает неизвестный format version в RW.

### 17.4. Checkpoint and ring occupancy

Seal ring capacity фиксируется mkfs и проверяется перед каждой транзакцией. High watermark trigger инициирует новый durable checkpoint. Нельзя перезаписывать protected checkpoint lineage, пока новое checkpoint не достигло `POWER_FAIL` seal. При нехватке места для checkpoint -> `ENOSPC_METADATA` и stop RW publication, а не опасный reuse slot. Checkpoint должен иметь подтверждённые все subordinate root bytes и текущие pending releases.

### 17.5. Repair policy

`ifsck inspect --read-only` по умолчанию, генерирует диагностический план и fingerprint исходного root. `ifsck repair --output <new-image>` строит **новый** image, оставляя старый без изменений; изменение рабочего устройства возможно только через explicit unsafe confirmation и backup. Никакого автоматического «исправления» двух противоречащих живых OID через удаление объекта без owner approval. Неизвестный формат/feature -> stop.

## 18. Boot layout, совместимость с IVX и обновления ОС

### 18.1. EFI bootstrap

Наша текущая UEFI Stage E загружает ядро из собственного ESP FAT16 image. Разработка IFS не требует переписывать UEFI или BootInfo v1. На этапах 1–3 root image IFS монтируется **как второй виртуальный диск QEMU** через native driver. После проверки read-only mount, recovery и runtime IVX будет выбран boot flow:

```text
UEFI firmware -> signed EFI loader on ESP (FAT)
-> verified native kernel -> BlockDevice driver
-> read-only IntellectFS system root verify
-> minimal trusted init / IVX loader
-> mount RW only after recovery/fence
-> login shell / network server / optional GUI
```

При использовании signed system image secure boot loader не может полагаться на недостоверный IFS root как якорь доверия. Root encryption unlock происходит без загрузки недоверенного кода из закрытого тома.

### 18.2. `IVX` и `IVL`

Файлы `.ivx` и `.ivl` — обычные immutable системные объекты с `EXECUTE_MAP`; **IFS не изменяет формат IVX-1**. FS выполняет byte integrity/storage policy, IVX loader — signature/ABI/capability/relocation policy. Для hot executable chunks предпочтительно хранить plaintext, 4-КиБ aligned, compression off или использовать validated decompression page cache. Когда `.ivx` подписан, изменение любого байта старой версии создаёт новый file object/version, а не патчит RX image in-place.

### 18.3. Native installation transaction

Установщик `.ivpkg` готовит файлы и closure зависимости в приватном namespace, проверяет IVX signatures и hashes, затем выполняет `fs_tx_seal(POWER_FAIL)` для **одновременной** смены namespace root и installation closure pointer. После crash либо старый набор приложений, либо новый. Persistent revocation/anti-rollback store **не** должен автоматически восстанавливаться вместе с обычным system snapshot.

### 18.4. Профили тома

`SYSTEM`: elevated metadata redundancy, immutable IVX, snapshot before update; `SERVER`: latency scheduling for DB + bounded gc; `DESKTOP`: hot-small files + optional transparent compression; `ARCHIVE`: compression and scrub prioritization. Профиль — политика, не отдельный несогласованный формат. Один код парсера и один invariants набор для всех профилей.

## 19. Feature flags и совместимость

### 19.1. Категории

- `required_features`: mount должен знать/поддерживать все биты.
- `ro_compat_features`: неизвестный бит запрещает RW, разрешает только RO при возможности безопасно прочитать базовые структуры.
- `compat_features`: неизвестный бит можно проигнорировать, **только** если его определение не меняет корректность базового чтения.

Первый формат v1 фиксирует отсутствие in-place metadata updates, отсутствие native multiwriter, отсутствие RAID parity hot stripe и отсутствие авторитетного external cache. Новые на-диске codecs и node kinds вводятся только с явно выделенными bits и независимой проверкой.

### 19.2. Формальная совместимость

Правило: `format_major = 1`, если wire-структуры и семантика сохраняются. Дополнительные поля не должны reinterpret старые bytes, reserved fields обязаны оставаться 0 до официальной feature activation. Никаких временных `v0→v1` migration внутри спецификации **первого ещё не реализованного формата**. После freeze изменение incompatible major будет отдельно проектироваться с copy/reformat, а не скрытым обновлением mount.

### 19.3. Backups и export

Backup pipeline читает verified snapshot root, копирует content-addressed immutable extents и canonical metadata descriptors с отдельным signed manifest. На другом устройстве физические pblk меняются, поэтому clone/export/restore **пересчитывает pointer hashes и строит новый volume root**; нельзя копировать блок pointers буквально и считать том переносимым, если `physical_block` входит в digest.

## 20. Проверяемые сценарии операций

### 20.1. Создание `/etc/service.conf` с заменой существующего файла

```text
client: fs_tx_begin(ROOT_VOLUME, snapshot_isolation)
client: fs_tx_mutate(CREATE new_oid in /etc/.service.tmp)
client: fs_tx_mutate(WRITE new_oid bytes[0..N), set logical_size=N)
client: fs_tx_mutate(SET_OWNER / SET_MODE to new_oid)
client: fs_tx_mutate(RENAME /etc/.service.tmp -> /etc/service.conf, replace=true)
server: reserve all data + metadata nodes + seal slot (preflight)
server: write immutable bytes and new OID/DIR/EXTENT/FREE tree nodes
server: write immutable commit descriptor and validate root refs
server: flush new bytes/metadata/descriptor
server: write seal record; flush seal
server: reply POWER_FAIL, tx_id, root_hash
server: defer release of previous service.conf extents until pins removed
```

Expected after crash at every position: `/etc/service.conf` is the **complete old version or complete new version**, not a zero-length replacement, mixed ranges or new entry without data, **subject to conforming device durability**. Hardlinks to replaced old oid are not implicitly updated: their file object identity remains old; replacement changes only the named directory entry.

### 20.2. Append two streams

Stream A reserves `[EOF, EOF+4096)`; stream B concurrently reserves next range with atomic append reservation. Both write immutable extents in parallel; commit merges `extent_index` and `eof` only after version validation. If `A` aborts and `B` commits, allocator can either create hole/sparse range or compact only with an explicit, safe reservation-release procedure; **never silently shift B bytes** after writer observed its reserved offset. API must document `APPEND_RESERVE` semantics independently from POSIX `O_APPEND`.

### 20.3. Directory rename

From `(parent1, "docs") -> OID_D` to `(parent2, "archive") -> OID_D` within same shard: preflight cycle check by parent graph, lock/version-check both parent directory objects and OID_D, remove old entry, create new entry, set parent OID_D = parent2, seal one root. Internal entries of the subtree remain keyed by stable parent OIDs; no recursive rewrite. For an ancestor-descendant attempt, fail `EINVAL_CYCLE` before reservation.

### 20.4. Atomic installation of IVX application

New `.ivx/.ivl` immutable bytes stored and verified by native loader; `install_generation` pointer published with one native IFS seal. Running process uses old pinned root. Crash after seal but before returned completion produces `UNKNOWN` to installer; installer queries tx_id and verifies `root_hash`, avoiding double activation. No executable code is modified in place.

### 20.5. Failed metadata allocation

If a tx has reserved data blocks but cannot reserve metadata for a B+Tree split and release queue, it fails before physical seal (`ENOSPC_METADATA`), retains old root, and the newly written data become orphans. It must **not** return success for the append and then emit ENOSPC while trying to make its name durable.

### 20.6. Corrupt data at valid pointer

Disk returns an extent payload whose checksum differs from the parent pointer. Parser marks it `CORRUPT`; if replica exists, reads replica and verifies it independently; if not, returns `EIO_CORRUPT` with `(oid, offset, extent pointer, expected hash)`. Never return zero-fill with code 0. Snapshots reusing this same damaged physical extent are also affected.

### 20.7. Fault during GC

Old root contains extent A; GC copies it as extent B. Crash before GC seal: A stays live and B is orphan. Crash after sealed pointer switch: B stays live and A remains pinned until safe frontier, then can be recycled. Crash during free-index update cannot produce A and B both reusable while live.

### 20.8. Fault during `WRITER_FENCE`

New owner may accept RW only after its fence reached `POWER_FAIL`. Crash before that point: mount recovery sees previous valid epoch, no user writes from new epoch could have been legitimately acknowledged. Crash after fence: new owner epoch is canonical. If previous owner is not externally stopped or fenced, this on-disk record **does not alone prevent concurrent writes**, and RW must be denied.

## 21. Процедуры восстановления и доказательство порядка (псевдокод)

### 21.1. `seal_power_fail(tx)`

```text
assert tx.has_valid_capability
assert tx.writer_epoch == active_durable_fence
assert tx.state == VALIDATED

reservation = allocate_preflight(tx, include_future_tree_nodes=true,
                                 include_descriptor=true, include_seal=true)
if reservation.failed: return ENOSPC_*  // nothing published

new_roots = build_private_cow_trees(tx, reservation)
if !validate_tree_closure(new_roots): return BAD_METADATA
if !validate_all_new_extent_digests(tx): return BAD_EXTENT

io = submit_writes(tx.data, tx.new_nodes, tx.commit_desc)
if !all_completed_successfully(io): return IO_AMBIGUOUS_OR_ERROR
if !blockdev.flush(DATA_AND_METADATA_DOMAIN).success: return IO_AMBIGUOUS

seal = assemble_seal(tx, new_roots, active_durable_fence, prior_seal)
assert next_slot_is_reclaimable_and_old_recovery_root_pinned(seal.slot)
if !blockdev.write(seal.slot, seal).success: return IO_AMBIGUOUS
if !blockdev.flush(SEAL_DOMAIN).success: return IO_AMBIGUOUS

// publication in memory can now be completed
publish_root_release(tx, new_roots)
return OK(POWER_FAIL, seal.digest, tx.id)
```

If the device reports unknown completion during `flush`, the in-memory publication policy must reconcile by reading back seal/descriptor and interrogating device capability; **ordinary readback alone does not prove power-fail persistence**. The client receives `UNKNOWN`, not a fabricated durable success.

### 21.2. `recover()`

```text
boots = read_fixed_bootstrap_copies()
boots = filter_full_digest_valid_geometry_and_compatible_features(boots)
if boots.empty(): return CANNOT_MOUNT_ORIGINAL_IMAGE

base = choose_consistent_bootstrap_group(boots)
anchor_candidates = read_bounded_anchor_checkpoint_slots(base)
root0 = choose_latest_valid_checkpoint(anchor_candidates)
if root0.none(): return CORRUPT_ROOT

state = root0
for candidate in bounded_tail_after(root0):
    if !is_valid_chain_successor(candidate, state):
        quarantine(candidate); continue_or_stop_by_policy()
    if candidate.kind == CROSS_PREPARE:
        remember_prepared_but_do_not_publish()
    elif candidate.kind == CROSS_COMMIT:
        if all_participants_and_desc_valid(candidate): apply_atomic_rootset()
        else: stop_or_ro(); do_not_partial_apply()
    elif candidate.kind == TX:
        validate_descriptor_and_root_metadata(candidate)
        apply_root_if_valid_and_parent_matches()
    elif candidate.kind == WRITER_FENCE:
        update_fenced_epoch_without_reusing_old_nonced_resources()

rebuild_transient_caches()
reconcile_allocation_reservations_and_deferred_releases()
return MOUNT_RO(state, recovery_report)
```

**Никакая** процедура `recover()` автоматически не активирует RW по одному валидному CRC. RW требует проверки повреждений, допустимых feature bits, отсутствия split-brain, fencing и пригодного durable device policy.

### 21.3. Фронтир сборки мусора

Пусть `P = {all live root generations, active snapshot roots, reader epochs, mapped IVX roots, oldest protected checkpoint}`. Пусть `reach(P)` — все физические диапазоны достижимых блоков. Условие освобождения:

```text
free_extent(e) allowed iff
  e not in reach(P)
  && e not in any in-flight reservation
  && e not in pending durable cross-shard prepare
  && e not in currently required recovery ring or bootstrap
  && the new FREE_TREE root listing e is safely sealed
```

Проверка `reach(P)` в горячем пути производится через reference accounting/deferred-release sequence, а периодический fsck подтверждает полным графовым обходом. Полный traversal на каждое освобождение не требуется, но невозможно считать refcount cache авторитетным, когда он расходится с опубликованным root.

## 22. Формальная модель и независимые тест-векторы

### 22.1. Минимальная абстракция

Состояние спецификации:

```text
S = (device_bytes, published_roots, reserved_blocks,
     live_blocks, orphan_blocks, snapshots, writer_epoch,
     journal_slots, pinned_checkpoints, pending_tx)
```

События: `Begin`, `Reserve`, `WriteBlock`, `CompleteIO`, `Flush`, `WriteSeal`, `SealAck`, `Crash`, `Recover`, `Read`, `Pin`, `Release`, `GC`, `SnapshotCreate`, `CrossPrepare`, `CrossCommit`. Неполное устройство моделируется недетерминированным сохранением подмножества записей перед flush и torn writes в любой позиции; **после достоверного flush** все предшествующие завершённые записи соответствующего domain устойчивы.

Safety properties: `R1..R10` и serializable namespace changes. Liveness properties отдельно: `eventual GC if space/IO available`, отсутствие starvation при fair fallback, bounded response на quota/cancellation. `Verus`/model checker не доказывают корректность NAND-контроллера, энергопитания и DMA, поэтому формальная проверка дополняется fault injection и аппаратными опытами.

### 22.2. Golden fixtures для on-disk формата

Зафиксированные строки magic и offsets уже являются обязательными целевыми решениями; изменять их разрешено **только до freeze** с согласованным обновлением всей спецификации и векторов.

### 22.3. Crash exploration matrix

Для каждого теста строим `old_state`, один или несколько tx, oracle допустимых root hashes, запись в виртуальный block device, произвольную точку stop, моделируемые reordering/torn writes, запуск `recover`, сравнение oracle. Обязательные сценарии:

- T-001 create new file, 1 byte, power fail до первого data write;
- T-002 после data write до pre-seal Flush;
- T-003 после pre-seal Flush до seal write;
- T-004 torn seal block (offset=1,255,4095);
- T-005 после seal write до final Flush;
- T-006 после final Flush до reply;
- T-007 success reply, crash, recovery = new or newer root при compliant device;
- T-008 `VOLATILE` Ack, crash до фонового flush = only old root;
- T-009 `ORDERED` Ack, seal исчезает = old root;
- T-010 old data block corruption after checkpoint = checksum error, not zero;
- T-011 rename old/new names within one tx = neither partial;
- T-012 delete last link with open handle = object lives until handle release;
- T-013 snapshot retained while GC frees old nodes = pin prevents reuse;
- T-014 two concurrent writes nonoverlap = both or explicit conflict, no lost update;
- T-015 repeated `tx_seal` after timeout = idempotent;
- T-016 `ENOSPC` while tree splits = no published incomplete entry;
- T-017 checkpoint ring wraps under load = protected version remains;
- T-018 crash while `ifsck --repair` = original remains intact;
- T-019 mount unknown feature = RO/reject per class;
- T-020 two RW writer epochs = reject without external fencing;
- T-021 async write cancellation after ambiguous DMA = NEVER false success;
- T-022 memory pressure OOM while hashing = previous state available;
- T-023 stale physical LBA inserted into another file = pointer hash fails;
- T-024 crash during snapshot delete = no premature block recycling;
- T-025 crash during GC move = exactly old or new pointer;
- T-026 crash during cross-shard prepare = invisible everywhere;
- T-027 crash after cross-shard coordinator = all visible or degraded RO;
- T-028 encrypted extent nonce reservation crash = nonce never reused;
- T-029 corrupted encryption key store = no plaintext leak, controlled failure;
- T-030 simulated lying Flush = test detects **limit of guarantees**, not a `POWER_FAIL PASS` claim.

### 22.4. Перебор, fuzzing и доказательные инструменты

- Differential parser: Rust reader, независимый строгий Python/C reference decoder и corpus golden vectors.
- Property-based generator для случайных деревьев, extents, quotas, OIDs, snapshots и tx graphs.
- LibFuzzer/AFL++ на host decoder и journal reader под ASAN/UBSAN; никаких «валидных» memory corruptions.
- Model checker (TLA+/PlusCal либо Alloy) для state transitions и all-or-none publication.
- CrashMonkey/ACE-подобные black-box test traces, но на **собственном raw image IFS**, не на kernel ext4.
- Verus или эквивалентный инструмент для локального proof-critical code (bounds, metadata parser, reference accounting, nonce reservation); proof не заменяет bounded crash testing.
- Независимая проверка, что *каждая* ошибка из негативных fixtures отклоняется до перехода в RW.

### 23.2. С чем сравнивать

На Ubuntu-host сравниваем IFS-образ через host-driver с аналогичным raw block backend и реальными ext4/XFS/Btrfs/ZFS **только с документированными эквивалентными параметрами**: sync level, checksums, snapshots, direct/buffered I/O, compression, RAM, SSD fullness, cache warm/cold. `POWER_FAIL` сопоставляется с действительно durable sync, а не с write() без flush. Нельзя утверждать, что IFS превосходит XFS в throughput, если один benchmark отключает гарантии, а другой включает полную проверку данных.

### 23.3. Target budgets — гипотезы

- При одинаковом SSD `p99` защищённого commit не должен неограниченно увеличиваться из-за чужого bulk I/O: per-priority bounded queue depth и stress gate.
- Метаданные одного независимого shard не должны блокировать чтения несвязанного shard из-за единственного глобального B-tree mutex.
- В обычном healthy case `recover` должен читать bounded tail и checkpoint, а не весь volume.
- Unencrypted, uncompressed, aligned sequential read должен поддерживать zero-copy/copy-minimising path, если подтверждена page integrity.
- Не назначать цифры `19×`, `29×`, `1.2 WAF`, `O(1) always` как release criteria без аппаратных измерений.

### 23.4. Отчётность

Каждый benchmark пишет `git SHA`, `format major/minor`, device model/firmware, logical/physical sector, capacity/fill %, memory, CPU cores, mount flags, durability semantics, I/O size+depth+threads, warm/cold, snapshot count, 99.9% confidence range, errors, recovery status. Скрипты не вызывают `dd` к физическим накопителям по умолчанию.

## 26. Архитектурные риски и конкретные контрмеры

| Риск | Почему возникает | Решение в IFS |
|---|---|---|
| Слишком тяжёлый CoW для DB 4K | metadata path copying, sync flush | small extents, batch tx, shard-local seal, отдельные direct-I/O policies |
| Потеря данных при «честном» software commit | контроллер кеширует write | pre-seal flush + post-seal flush; explicit durability evidence |
| Ложная гарантия при lying flush | устройство нарушает контракт | документировать предел, device qualification, redundancy/UPS как дополнение, не доказательство |
| Root publish torn | 4 KiB не обязательно atomic | multiple slots + checksum/digest + old pinned checkpoint |
| Нечестное свободное пространство | bitmap расходится с CoW root | один committed allocation root + reconciliation |
| ENOSPC после половины commit | underestimated metadata/GC reserve | preflight upper-bound, staged aborted tx, protected emergency reserve |
| Голодающие OCC writers | повторные conflicts | fair fallback lock per object/shard |
| Rename миллионов потомков | full path in tree | OID + parent,name index |
| Cross-shard inconsistent rename | два независимых seals | explicit coordinator all-or-none or EXDEV |
| Неконтролируемый fsck | damaged tree triggers cycles | strict depth/visited set/work budgets |
| Snapshot pin explosion | старые extents не освобождаются | quotas/pin limits, age policy, hard reserve |
| Self-encryption nonce reuse | crash replays counters | durable nonce reservation fence, burn unused ids |
| Compression bomb | wrong logical length | bounded verified decode budget |
| VFS/IVX inconsistencies | format hash mistaken for signature | separate FS integrity, IVX signature and launch policy |
| «Супербыстрота» за счёт unsafe bypass | missing ACL/hash/bounds | fast paths only after same verification |
| Microkernel FS service crash | state lost in user process | immutable core, restart from last durable seal, single writer fence |
| Disk bit rot without replica | checksum detects, cannot heal | report corruption; verified backup/scrub/mirror optional |
| Power failure during update | mixed IVX versions | native namespace + installation closure in one seal |
| New architectures 16/64KiB pages | kernel physical page != 4KiB FS block | separate block abstraction, buffer slicing, tests on supported arch |

## 27. Окончательные принятые решения и ещё не замороженные детали

### 27.1. Архитектура утверждена для дальнейшей разработки

1. **Имя:** IntellectFS, локальный формат `IFS-1`, профиль для IntellectOS, не Linux fork.
2. **Нативный tx API:** `begin -> mutate -> seal`, уровни `VOLATILE`, `ORDERED`, `POWER_FAIL`.
3. **Persistent publication:** CoW data+metadata, immutable descriptor, ordered flush, проверяемый 4-КиБ seal, final flush для durable ACK.
4. **Object identity:** OID без полного пути; directory index `(parent_oid,name) -> oid`.
5. **No in-place live updates**, включая свободное пространство, CoW roots и IVX executable blobs.
6. **One canonical state:** проверенная seal chain и подчинённый root-set; все cache/bitmap — вторичны.
7. **Root integrity:** поочерёдные проверяемые 4-КиБ bootstrap/seal, BLAKE3-256 parent pointers, bounded recovery.
8. **Allocation:** shard/AG isolation, metadata reserve, preflight ENOSPC, snapshots + GC pins.
9. **Portability:** 4-КиБ on-disk block **не означает** atomic write requirement или CPU page size.
10. **Single RW owner v1:** writer_epoch/fence предусмотрены сразу; многохостовый RW не активируется без независимого fencing и протокола согласования.
11. **IFS не использует ИИ в critical path** и работает без GUI, UINTR, CXL, FDP, eBPF, network и NVMe-specific atomic promises.
12. **IVX integrity отдельно от FS integrity**; никаких `.vbin`, ELF как пользовательский native format или обязательного JIT при загрузке.
13. **Первый код — host-side verifier / crash engine**, затем QEMU backend и только затем аппаратная интеграция.

### 27.2. Технический freeze gate — обязательные до записи production RW

Эти вопросы нельзя замолчать, хотя архитектурная стратегия уже выбрана:

- независимый audit exact bytes всех structs (`IFSBootstrapV1`, `IFSSealV1`, `IFSPointerV1`, `IFSNodeV1`, `IFSCommitDescV1`) и golden vectors BLAKE3/CRC32C;
- формализация `IFSLayoutManifestV1`: immutable roots, ranges всех shard rings, AG ownership, запрет overlap и алгоритм bootstrap от глобального anchor к каждой local chain;
- окончательная схема `ObjectRecordV1`/DirRecord/ExtentRecord и кодов feature bits;
- reference-count semantics относительно snapshots, recovery checkpoint, pinned read epochs, lazy mmap и detached IVX;
- checkpoint ring size policy and overflow bounds, max transaction limits, cross-shard coordinator state machine;
- backend-specific `durability_evidence` и команда Flush/FUA на AHCI/virtio-blk/NVMe;
- политика CSPRNG/nonce reservation и независимый key service;
- выбранная host language/toolchain, reproducible build/fuzz/proofs, экспортируемый C ABI;
- offline test of disaster recovery with secondary copies and hostile power-failure simulator;
- независимые доказательные тесты, которые могут **опровергнуть** заявленные гарантии.

Важно: открытые детали **не** дают права авторам реализации придумывать несовместимый layout без изменения данного спецификационного документа и повторной проверки. Этот документ является целевой самодостаточной архитектурной базой; не объявляется математически завершённым стандартом до freeze gate.

## 28. Проверка предложений другого ИИ: принятые, изменённые и отклонённые

| Предложение | Наше решение | Обоснование |
|---|---|---|
| Один `begin → mutate → seal` | **ПРИНЯТ** | ясный native crash contract |
| Три уровня `volatile/ordered/power-fail` | **ПРИНЯТ С УТОЧНЕНИЕМ** | volatile RAM-only ack; ordered physical data-first; power-fail requires honest device flush |
| «Один атомарный блок 4KiB» | **ИЗМЕНЕНО** | 4KiB — *логический размер*; physical atomicity не предполагается |
| OID вместо full-path tree | **ПРИНЯТ** | directory rename без переписывания поддерева |
| Один source of truth + cache rebuild | **ПРИНЯТ** | allocator tree входит в committed root, shortcut caches не авторитетны |
| `(paddr,length,generation,checksum)` | **ПРИНЯТ И РАСШИРЕН** | 128-byte typed pointer, physical binding, owner offset, cipher/tag |
| Parent AEAD tag | **ПРИНЯТ** | tag хранится в pointer, но только при включённом ENC |
| Nonce из owner/gen/offset | **ИЗМЕНЕНО** | нужен **durable never-reused reservation**, иначе retries после crash повторят nonce |
| Большие данные вне Bε nodes | **ПРИНЯТ** | inline до 256 bytes, большие immutable extents |
| Независимые shard allocators/seal writers | **ПРИНЯТ** | cross-shard coordinator и fallback lock обязательны |
| Один файл — параллельная запись без lock | **УТОЧНЕНО** | disjoint prep параллельна; EOF/metadata version требуют merge/serialization |
| Writer epoch в формате сразу | **ПРИНЯТ** | durable epoch/fence; multiwriter RW v1 запрещён |
| Multiple superblocks | **ПРИНЯТ** | 4 fixed copies и ring/checkpoint chain |
| Unknown required feature → no RW | **УСИЛЕНО** | unknown mandatory → no mount; ro_compat → RO |
| GC и capacity reserve | **ПРИНЯТ** | hard reserve, quotas, ENOSPC preflight |
| No write hole in parity RAID | **ПРИНЯТ КАК ЗАПРЕТ** | parity RAID не входит в v1; без sealed stripe policy он запрещён |
| UINTR/MPK/FDP/CXL лишь performance hints | **ПРИНЯТ** | Linux/Intel-specific capabilities не входят в on-disk correctness |
| Диск как недоверенный ввод | **ПРИНЯТ** | bounded verification до dereference |
| Утечка допустима, потеря нет | **С УТОЧНЕНИЕМ** | orphan допустим; при тотальном отказе SSD/lying flush абсолютной гарантии нет |
| Verus как единственная гарантия | **ОТКЛОНЕНО** | proofs + crash fault injection + independent hardware tests |
| Гарантия восстановления только по dirty tail | **УТОЧНЕНО** | fast normal recovery bounded, deep repair может быть O(volume live data) |
| Fast path через Linux FUSE/io_uring | **ОТКЛОНЕНО КАК ЗАВИСИМОСТЬ** | в IntellectOS собственный BlockDevice/VFS ABI |
| Сеть FoundationDB/RDMA для локальной root FS | **ОТЛОЖЕНО** | сложность, не отвечает задаче native single-host boot volume |

## 30. Условия принятия окончательной спецификации в проекте

Этот файл **можно использовать сейчас как исходную архитектурную директиву** для разработки IntellectFS. Он не является разрешением записывать данные пользователей в опытную ФС и не является завершённым binary interoperability стандартом.

Статус переходит из `DESIGN DRAFT` в `FORMAT FROZEN` только когда:

1. Существует независимое согласованное описание всех обязательных record layouts и feature-bit registry.
2. Существуют и прошли минимум два независимых strict parser implementations, golden vectors и negative tests.
3. Модель `Crash -> Recover` доказала R1..R10 на заданной adversarial block semantics, включая torn 4-KиБ writes и reordering.
4. `mkifs`, `ifsck --inspect` и crash simulator работают на **обычном файле** без физического накопителя.
5. Нет unresolved self-reference в allocator/descriptor/hash/nonce design.
6. Cross-shard reader visibility и порядок merge/fallback документированы через state transition traces.
7. Обязательно проверены все bounds/cycle/resource limits, включая поддельные шардовые метаданные.
8. Описан профиль устройства, на котором `POWER_FAIL` имеет смысл, и тесты не принимают успешный `write()` за durability.
9. Проведено независимое code/security review, а обнаруженные противоречия исправлены **внутри данного документа**, не через россыпь приложений с конкурирующими правилами.
10. Лишь после этого допускается реализация RW prototype на QEMU; аппаратная эксплуатация требует отдельных испытаний.

**Итог:** IntellectFS — быстродействующее, объектно-ориентированное, copy-on-write хранилище для **нашей собственной IntellectOS** с native transactional API, проверкой целостности, строгой устойчивостью публикации и измеримыми оптимизациями. Фундамент не зависит от Linux, GUI, ИИ, конкретного производителя CPU или SSD. Производительность подчинена корректному контракту данных, а не наоборот.
