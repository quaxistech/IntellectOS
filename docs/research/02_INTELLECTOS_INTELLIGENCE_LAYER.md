# IntellectOS — интеллектуальный слой ОС и модель безопасной автономности

**Версия проектного документа:** 1.0 · **Статус:** DESIGN DRAFT · **Назначение:** интеллектуальная ОС, работающая самостоятельно и предсказуемо даже при отсутствии модели или сети.

## 1. Что делает ОС интеллектуальной

Интеллект не означает, что любая функция ядра — нейросеть. Основная идея: IntellectOS умеет понимать цель пользователя, объяснять состояние машины, организовывать задачи, предлагать и готовить изменения, анализировать программные ошибки и (при наличии разрешений) выполнять автоматизацию. Каждый такой путь ограничен проверяемым планом и системными полномочиями. Модель не может переписать page table по текстовому запросу и не решает, какие байты исполняемого файла считать подписанными.

| Режим | Без нейросети | С нейросетью |
|---|---|---|
| Загрузка ОС / IVX | **работает** | не требуется |
| Управление процессами | **работает** | диагностика и советы |
| Файлы и сеть | **работают** | семантический поиск и автоматизация по правам |
| Компиляция Vibelang | детерминированный компилятор **должен работать** | дополнительные генерация и оптимизации |
| Отладка/профилирование | трассы, perf-счётчики и лог | объяснения, поиск причин, подбор исправлений |
| Пользовательские действия | CLI/GUI | диалог/агент с подтверждением опасных действий |

## 2. Архитектура слоёв

```
User Intent (GUI / CLI / voice / API)
              │
         Intent Gateway
              │  идентичность, контекст, policy
              ▼
       AI Planner / local LLM
              │  ТОЛЬКО Proposal IR
              ▼
      Proposal Validator
        ├─ schema/type checks
        ├─ effect/capability audit
        ├─ input provenance / prompt-injection boundaries
        ├─ resource admission
        └─ required approvals
              │
              ▼
      Deterministic Executor
        ├─ OS typed APIs
        ├─ Vibelang compiler tools
        └─ user-provisioned scoped handles
              │
              ▼
      Receipts / Audit / Undo (where possible)
```

AI Planner не получает прямых дескрипторов системных ресурсов. Полученные из файлов, веб-страниц и приложений тексты — **данные**, не системные инструкции. Exec слой никогда не запускает shell-команду из «плана» без отдельного синтаксического/политического контракта и авторизации соответствующей операции.

## 3. Основные AI-сервисы

1. **OS Assistant:** интерактивные задачи, настройка, поисковые операции, помощь в интерфейсе.
2. **System Health Agent:** анализ диагностических событий, предупреждения о деградации CPU/RAM/IO, предложения настройки. Не устраняет ошибки автоматически без разрешения.
3. **Developer Agent:** генерация `.vibe`, создание VSG, оптимизация VBIR, объяснение ошибок компиляции и профилей.
4. **Performance Agent:** PGO-профили, пробы альтернативных layouts, компромиссы энергопотребления и латентности. В продакшене включается только измеренная безопасная версия.
5. **Knowledge Indexer:** семантическое индексирование пользовательских разрешённых источников с контролем границ данных.
6. **Automation Broker:** планируемые разрешённые действия в строго заданном пространстве ресурсов; отмена, квоты, наблюдаемость.
7. **Security Adviser:** анализ аномалий, рекомендации администраторам; итоговые allow/deny решения принимает policy engine, не нейросеть.

## 4. Типизированная операция агента

Предлагаемая схема `ActionProposalV1` (текстовое представление для документации; wire-форма отдельно версионируется):

```
proposal_id: content-hash
principal_id: authenticated principal
objective: user-visible description
operation: closed enum, e.g. file.read | process.inspect | build.compile
resource_ref: opaque scoped handle/token, not path guessed by model
arguments: typed operation-specific payload
requested_rights: minimum rights
preconditions: expected generations and current state
limits: time, CPU, memory, I/O, retry count
approval_class: none | user | administrator
on_failure: stop | explicit bounded retry | rollback if supported
```

Идентичность principal и разрешения **добавляет доверенная платформа**, а не нейросеть. Приложение не может изменить `approval_class` через промпт или конфигурацию собственной команды. `preconditions` защищают от применения старого плана к уже изменившемуся состоянию; нет «best effort» на непроверенном идентификаторе устройства.

## 5. Классы автономности

| Уровень | Пример | Требования |
|---|---|---|
| L0 Observe | показать занятую память | read-only handle, лимиты |
| L1 Suggest | предложить оптимизацию | никакого системного изменения |
| L2 Prepared | сгенерировать патч в sandbox | изолированная запись в staging, review |
| L3 Bounded Act | переименовать явно выбранный файл | проверка rights, подтверждение по политике, receipt |
| L4 Privileged Act | изменить boot policy/firmware/driver | отдельный администратор, out-of-band/secure confirmation |
| L5 Autonomous System Change | автоматическая замена ядра/политик | **не разрешается** в базовом V1 |

Пользователь может запретить запуск AI-процессов целиком; базовая ОС остаётся работоспособной. Управление ресурсами AI выполняется как для обычных процессов: quotas, NUMA/accelerator placement, confidential memory policy, kill/restart.

## 6. Local-first и приватность

Модель может быть локальной. При обращении к внешнему провайдеру сеть/передача контекста требует прозрачного разрешения и политики данных. Не экспортировать по умолчанию секреты, имена приватных файлов, содержимое памяти процессов, ключи шифрования и снимки окон. Предусмотреть per-app consent, per-source retention, clear export preview и явное отключение телеметрии.

Изоляция модельного inference: отдельный процесс, минимальные privileges, read-only веса, limit memory/accelerator, sandbox для расширений, никаких доступов к ядру/подписи без брокера. При таймауте/ошибке модельного вызова — ограниченный возврат ошибки без задержки критического пути scheduler/IO.

## 7. Интеллектуальное управление кодом

AI предлагает `SourcePatchProposal`, `VSGCandidate` или `OptimizationProposal`, содержащие ожидаемую цель, область изменений, наблюдаемое поведение, тесты/предусловия и hash предыдущей ревизии. Надёжность обеспечивается обычным компилятором: парсер, type/effect/ownership checking, VBIR verifier, codegen, linker, IVX verifier. Гипотезы «ускорим на 70%» принимаются только после профилирования в изоляции; некорректная оптимизация отклоняется и не заменяет предыдущую хорошую сборку.

## 8. Управление памятью и аппаратной эффективностью

AI Advisory Loop: собрать системные метрики (с допустимой дискретизацией), классифицировать workload, предложить параметры (worker count, placement, prefetch, background throttling), выполнить A/B тест или заранее выделенный benchmark, приёмка по p50/p95/p99, энергопотреблению и памяти, rollback при регрессии. OS scheduler сохраняет hard limits: AI рекомендация не меняет MMU/user rights и не отключает проверку страниц.

## 9. Устойчивость и Recovery

Возможные отказы: модель недоступна, GPU OOM, hallucinated action name, зацикленные предложения, prompt injection из файла, ошибочный profile, конфликт ревизий, потеря сети. Обработка: fail-closed на новые привилегии, bounded retries только идемпотентных операций, отдельные записи ошибок, остановка и освобождение ресурсов агента, возврат к CLI/manual flow. Никогда не зацикливать reboot/repartition/install по неудачному AI-плану.

## 10. Аудит и согласие

Receipt должен содержать идентификатор авторизовавшего пользователя, operation enum, canonical аргументы с маскировкой секретов, связанные hashes/revisions, результат и точную системную ошибку. При необратимых действиях показывать превью изменяемых ресурсов. Для массовых действий использовать dry-run и bounded count; кнопка отмены/kill agent не должна ждать завершения нейросети.

## 11. Интерфейсы компонентов

Предлагаемые роли:

- `intelligence.plan(intent, scoped_context) -> proposal`
- `policy.validate(proposal, principal) -> verdict`
- `approval.request(verdict, human_context) -> approval_token`
- `executor.apply(validated_proposal, token) -> receipt`
- `telemetry.read(scoped_query) -> bounded_metrics`
- `compiler.optimize(vbir_hash, goals) -> candidate_hash`

**Это логические RPC-контракты, не работающие сегодня вызовы.** Их wire ABI, криптографические scopes и error lists определяются при реализации user-space IPC.

## 12. Acceptance Gates

- При полном отключении inference ОС загружается и выполняет подписанный IVX.
- Ввод из недоверенного файла не может получить `administrator` права.
- Любое исходящее сетевое обращение от AI имеет проверяемое consent/policy.
- Неподдержанная операция отвергается до исполнения.
- Все действия ограничены ресурсами и имеют interruptible timeout.
- Экспериментальная оптимизация не активируется без компиляторных проверок и измерений.
- `deny` policy невозможно заменить на `allow` посредством ответа нейросети.
- Возможны rollback и детерминированная ручная диагностика без участия модели.

## 13. Этапность

A0: формальная модель proposal/rights и offline executor harness; A1: наблюдение/диагностика read-only; A2: локальный inference user service и consent; A3: agent-assisted разработка Vibelang; A4: безопасные bounded actions; A5: профилирование/рекомендации; A6: расширение контекстной интеллектуальности. Все этапы идут **после** необходимых kernel-memory/user-isolation gates.
