# Intellect OS

**Experimental bare-metal operating-system research — BIOS Foundation 0.4 + UEFI Stage E.**

Intellect OS currently has **two independent native boot paths**, without Linux or GRUB on the target machine:

- **Legacy BIOS:** custom MBR and Stage1 load a freestanding 32-bit x86 kernel (protected mode).
- **UEFI x86-64:** custom `BOOTX64.EFI` gathers platform information, prepares a native 64-bit kernel, obtains a fresh memory map, calls `ExitBootServices()`, and transfers execution to an independent kernel that draws directly to the framebuffer.

Both produce the **Intellect BootInfo ABI v1** (152-byte header; separate 24-byte normalized memory records), but the BIOS and UEFI kernels are currently **distinct binaries**.

## Verified status

- Current `make clean check` baseline: BIOS and UEFI image verification, the full `tests/` suite (72 tests), and the `host_tests/` suite (15 tests) pass.
- Memory Core M1 D2 has QEMU/OVMF and Lenovo observations. M2 and M3-A have host-tested implementations; they must not be described as QEMU/Lenovo-verified without a recorded runtime smoke gate.
- **QEMU/OVMF Stage E:** native x86-64 kernel screen observed after `ExitBootServices()`.
- **Physical Lenovo IdeaPad (AMD A6-9225):** native x86-64 kernel screen observed, including `BOOTINFO ABI: V1 VALIDATED` and `NATIVE KERNEL RUNNING`. The same machine previously booted the BIOS 0.4 i386 kernel.
- These are **observational runtime checks**, not formal validation of every code path, arbitrary firmware implementation, page table, or driver.

At this stage there is **no installer, filesystem, persistent storage driver, multitasking, user-space applications, runtime AI, or autonomous code generation**. The kernel reports hardware details then halts the boot CPU. This is a research prototype, not a general-purpose OS.

## Build on Ubuntu 24.04

```bash
sudo apt update
sudo apt install -y build-essential binutils clang lld llvm make python3 \
    qemu-system-x86 ovmf

cd /home/quaxis/IntellectOS
make clean check
```

The generated files are all under `build/` and are **not tracked in Git**.

| Command | Purpose |
|---|---|
| `make check` | Build BIOS and UEFI images, verify layout and run all host tests |
| `make run` | Launch BIOS 0.4 image in QEMU |
| `make run-headless` | Launch BIOS QEMU with serial output in terminal |
| `make uefi-e-run` | Launch UEFI Stage E in QEMU/OVMF |
| `make clean` | Remove generated files under `build/` |

To run UEFI Stage E:

```bash
make uefi-e-run
```

Expected independent kernel banner:

```text
INTELLECT OS - NATIVE X86-64 KERNEL
UEFI STAGE E / INDEPENDENT EXECUTION
EXITBOOTSERVICES: SUCCESS
BOOTINFO ABI: V1 VALIDATED
NATIVE KERNEL RUNNING - CPU HALTED
```

The message is generated by the native kernel after `ExitBootServices()`. No EFI console calls occur afterward.

## USB images and safety

- BIOS image: `build/intellectos-bios.img`.
- UEFI image: `build/intellectos-uefi-stage-e.img`.
- Both are **32-MiB raw disk images**, not ISO files. Image builders only create files in `build/` and never invoke `dd` or access `/dev/sd*`.
- Writing an image to a USB device overwrites that device. Verify its model, transport, and device path immediately before any manual write. **Never use your development workstation's system SSD as the target.**
- UEFI image is unsigned; Secure Boot policy can reject it. BIOS/UEFI boot selection is decided by firmware.
- Experimental hardware execution may hang or require a power cycle. Do not store important data on the test computer.

See [hardware verification](docs/HARDWARE_TEST.md).

## Engineering boundaries

The identity-map bootstrap pages, single-core halt loop, memory classification and BootInfo handoff are not a production-quality memory manager or security boundary. There are no schedulers, user-mode privileges, general device drivers, USB HID, or ACPI runtime control. ACPI and SMBIOS addresses are reported, **not** deeply parsed or assumed safe to dereference after firmware exit.

For the implementation details and limitations, see [Architecture](docs/ARCHITECTURE.md), [BootInfo ABI](docs/BOOTINFO_V1.md), [Stage E design](docs/UEFI_STAGE_E.md), [test history](docs/MILESTONES.md), and [roadmap](docs/ROADMAP.md).

## Memory Core Foundation (M1 D2 verified)

The verified M1 D2 foundation adds a fail-closed low-4-GiB physical-page allocator,
IDT/GDT/TSS exception diagnostics and a 512-KiB runtime ELF linker bound.
See [Memory Core Foundation](docs/MEMORY_CORE_FOUNDATION.md) for ownership
assumptions and the QEMU/Lenovo acceptance sequence. The historical 23-test
Stage E checkpoint above remains a **prior** observation, not a validation of
these new changes. No BIOS implementation or BootInfo v1 layout is changed.

## Memory Core M1 D2 (verified on QEMU and Lenovo, 2026-11-19)

This stage fixes the Stage E native-entry register handoff and adds an
NX-enforced supervisor-only high-half scratch VMM window with 4-KiB mappings.
It does not yet implement global W^X, guard pages for the kernel stack,
full kernel virtual-memory isolation, or a kernel heap. See
[Memory Core M1](docs/MEMORY_CORE_M1.md).

## Current implementation checkpoints

- M2: bounded single-CPU kernel heap, candidate and host-tested.
- M3-A: bootstrap identity-paging hardening, candidate and host-tested.
- C1: kernel COM1 monitor and command parser.
- H1/H2: hardware discovery and guarded bootstrap driver framework.
- S0: read-only ATA PIO/block/partition backend.
- B1/L1/I2/U1: boot menu, live welcome image, FAT32/IFS installation foundations and a static user-ring terminal.
- AI/compiler/IVX: specifications and selected host format/installation foundations exist, but no general Vibelang toolchain or general-purpose IVX application ecosystem is implemented.
